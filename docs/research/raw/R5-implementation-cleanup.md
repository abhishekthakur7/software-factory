### RQ-S4-1. What do labs and tool vendors say about keeping an agent's implementation conformant to an approved plan, and what evidence of drift exists?

**Answer.** Vendor guidance is architectural, not procedural: Anthropic's agent-building guidance recommends decomposing work into checkpointed sub-tasks with human-in-the-loop pauses at irreversible actions, and Claude Code operationalises this as a plan produced in a read-only "plan mode" followed by an explicit approval step before edits begin. There is no published vendor-side measurement of how often implementation actually matches an approved plan; what exists instead is user-reported drift (Claude abandoning parts of an approved plan after exiting plan mode) and a growing academic literature on agent "derailment" — where an agent takes a wrong turn mid-trajectory and does not recover on its own. Independent research on agent-generated pull requests shows agent PRs are accepted at meaningfully different rates by tool (55%–86% across five agents in one dataset), with "oversized PR" and "experimentation-only" submissions appearing as agent-specific (not human-specific) rejection reasons — an indirect signal of scope/plan drift.

**Patterns found.**
- Task decomposition + human checkpoints at irreversible actions — "Building effective agents," Anthropic, https://www.anthropic.com/research/building-effective-agents (referenced via secondary summaries; primary is Anthropic's engineering blog), company practice doc. No measured drift rate given.
- Plan mode: explore/plan in a read-only mode, explicit approval gate before file edits — Claude Code documentation and product write-ups, https://claudelog.com/mechanics/plan-mode/ and https://www.anthropic.com/engineering/claude-code-auto-mode, company practice doc / lab doc.
- Reported plan abandonment after exiting plan mode — GitHub issue "Claude code drifts from plan mode," https://github.com/anthropics/claude-code/issues/32253, practitioner report (anecdotal, single-source, unresolved at time of search).
- Anthropic's internal agentic-misbehavior incident log (overeager/unintended initiative, e.g. deleting branches, attempting a production migration) — "How we built Claude Code auto mode," Anthropic, https://www.anthropic.com/engineering/claude-code-auto-mode, company practice doc. Anecdotal incident examples, not a rate.
- Agent trajectory "derailment": agents make early correct progress then follow unproductive paths and do not self-correct; a process reward model (PRM) is proposed to detect and intervene mid-trajectory — "When Agents go Astray: Course-Correcting SWE Agents with PRMs," arXiv:2509.02360, https://arxiv.org/abs/2509.02360, peer-reviewed/arXiv paper. Exact derailment-rate and PRM-lift figures were not extractable from the fetched excerpt (see Gaps).
- Agentic PR acceptance rates by tool, from a large mined dataset (AIDev): OpenAI Codex 85.8% of 20,993 PRs, GitHub Copilot 55.0% of 3,891, Cursor 74.6% of 1,347, Claude Code 71.3% of 380, Devin 55.5% of 4,673, human developers 82.6% of 6,149; agent-specific rejection reasons include "oversized PR" (1.5% vs 0% for humans) and "experimentation-only" submissions (2.9% vs 0.9%) — "Why Agentic-PRs Get Rejected: A Comparative Study of Coding Agents," arXiv:2602.04226, https://arxiv.org/html/2602.04226v1, peer-reviewed/arXiv paper. Measured, denominators given per row.

**Evidence quality.** Mixed. Vendor architecture guidance is primary but non-quantitative (no published conformance rate). The drift-after-plan-mode claim is a single anecdotal practitioner report (a GitHub issue), not corroborated by a second independent source in this search. The PR-rejection and derailment papers are primary, measured, and give real denominators, but they measure downstream symptoms (rejection, non-recovery) rather than plan-conformance directly — no paper found that measures "% of implementation lines/decisions that match the approved plan."

**Transfer to an agent.** The pattern (decompose into checkpointed steps, gate on plan approval, re-surface the plan before merge) transfers directly to S4/S5 of the factory. Proposed pipeline rule: S4 exit requires the agent to diff its own trajectory against the S3 plan's declared file/module list and produce a structured deviation list (see RQ-S4-5) rather than relying on the human to notice drift by rereading the diff (P4, P9).

**Gaps.** Searched for: a lab-published conformance metric ("% of plan followed"), and Anthropic/OpenAI/Cursor documentation specifically about re-reading or re-anchoring to a plan mid-task. Found architecture description but no measured drift rate. The PRM paper's exact derailment percentage and post-intervention lift could not be extracted from the fetched PDF text (binary/formatting issue); a follow-up fetch of the HTML version or a secondary summary would be needed for the numbers.

### RQ-S4-2. What do major style guides say about when a comment is required and when it is forbidden, and is any of it mechanically checkable?

**Answer.** Google's style guides and Ousterhout converge on the same rule stated two ways: a comment must add information the code cannot express itself (why, not what; the "why" a Python line or a design choice exists; anything "tricky, non-obvious, interesting, or important"), and a comment that merely restates the code at the same level of abstraction is forbidden as noise. Google's C++ guide additionally makes one comment class mandatory and mechanically checkable in form (TODO comments must include the string "TODO" and an identifiable owner). The forbidden case — restating the code — is partially checkable today via static-analysis lint rules that flag commented-out code (e.g., SonarQube S125), but no lint that reliably detects "this comment is semantically redundant with the line below it" was found; that judgment still requires an LLM or human reader.

**Patterns found.**
- Function/declaration comments are required and should describe behavior and inputs/outputs, not restate the implementation; implementation comments are required only where something is "tricky, non-obvious, interesting, or important" — Google C++ Style Guide, "Comments," https://google.github.io/styleguide/cppguide.html (fetched via secondary summary at https://guiquanz.gitbooks.io/google-cc-style-guide/content/ebook/Comments.html), company practice doc.
- TODO comments are required to carry an identifier (name/email) of who can give context, and the string TODO in caps — same source, company practice doc. Mechanically checkable (regex/lint for TODO format is standard in CI).
- Comments should describe what is not obvious from the code; comments at the same abstraction level as the code are "likely to repeat the code itself and thus useless" — John Ousterhout, *A Philosophy of Software Design*, summarized via https://danlebrero.com/2021/02/24/philosophy-of-software-design-summary/ and https://masalmon.eu/2023/10/19/reading-notes-philosophy-software-design/, book (practitioner), secondary summaries of a primary book (book itself not directly fetchable).
- Ousterhout explicitly disputes the "Clean Code" position that every comment is a failure, arguing code cannot express everything a reader needs — same source.
- Mechanical detection of the forbidden case ("commented-out code," a narrower proxy for redundant/dead comments): SonarQube rule S125 ("Sections of code should not be commented out"), https://community.sonarsource.com/t/semi-colons-in-comments-detected-as-commented-out-code/60414 and https://next.sonarqube.com/sonarqube/coding_rules?open=csharpsquid%3AS125, tool documentation/community reports. Known to produce false positives on ordinary comments containing code-like punctuation (practitioner-reported, not a published precision figure).

**Evidence quality.** Primary for the Google style guide (official doc, fetched); secondary summaries for the Ousterhout book (the book itself was not fetched, but summaries agree closely enough on wording that the pattern is high-confidence). Two independent practitioner sources agree. No published precision/recall figure exists for redundant-comment detection specifically; the S125 evidence is anecdotal community reporting, not a measured study.

**Transfer to an agent.** Directly transferable as a rubric line for S5 (FM-12, FM-13): a comment fails the rubric if it can be regenerated word-for-word by paraphrasing the adjacent code (mechanical proxy: high lexical overlap between comment and the statement/identifier names it precedes), and a comment is required wherever the agent's own plan (S3) marked a decision as non-obvious or where behavior deviates from what the code's name/signature implies. TODO-style comments should be lint-enforced at S5 for owner-identifier presence.

**Gaps.** Searched for a mechanically-validated "redundant comment" detector with published precision/recall; none found — existing lints (S125 and equivalents) only catch commented-out code, not paraphrase-redundancy. Searched for Ousterhout's original text directly (book, not freely available online) and relied on multiple independent secondary summaries instead — noted as a limitation.

### RQ-S4-3. How do organisations judge test quality beyond coverage, and what criteria did Meta use to accept or reject generated tests?

**Answer.** Beyond line/branch coverage, the two dominant measured techniques are mutation testing (does the suite actually kill synthetic faults, not just execute the lines) and human/engineer acceptance review after automated filtering. Meta's TestGen-LLM is the most concretely documented case: it generates candidate tests with an LLM, then mechanically filters them through a build-success filter, a reliable-pass filter (no flakiness), and a coverage-increase filter, and only tests that clear all three are shown to an engineer for a final accept/reject decision — this pipeline is explicitly built to eliminate hallucinated or filler tests before any human sees them (P6 in the charter's language). Google's older "Test Certified" program measured test *culture* rather than individual test quality, via a three-level rubric of practices (size/speed balance, coverage floors, no build-breaking tests) that teams had to satisfy to advance a level.

**Patterns found.**
- TestGen-LLM's three-stage acceptance filter (build → pass reliably → increase coverage), evaluated on 86 Kotlin components (31 Stories, 55 Reels): 75% of test classes had at least one new test case that built correctly, 57% had at least one that built and passed reliably, and 25% had at least one that built, passed, and increased line coverage — "Automated Unit Test Improvement using Large Language Models at Meta," arXiv:2402.09171, https://arxiv.org/abs/2402.09171 (figures confirmed against full text via https://r.jina.ai/https://arxiv.org/pdf/2402.09171), peer-reviewed/industry paper (FSE 2024). Measured, denominator = 86 classes.
- Test-a-thon deployment: across three test-a-thons, TestGen-LLM was applied to 1,979 test classes and successfully improved 196 of them (~10%; the paper's abstract separately reports "11.5%," a discrepancy this research did not resolve — see Gaps); 73% of the test improvements it proposed were accepted by developers for production — same source. Measured, denominators given (196/1,979; 73% of proposed improvements).
- One documented single test-a-thon event: 36 engineers landed 105 unit-test diffs in one Instagram test-a-thon, of which TestGen-LLM authored 17 diffs and 16 landed — same source. Measured, small-sample.
- Mutation testing as the standard "beyond coverage" quality signal: a surviving mutant indicates a code change no test in the suite would catch, catching boundary-condition, operator, and weak-assertion bugs coverage misses; PIT is the Java-ecosystem standard, Stryker for JS/TS/C#/Scala — QASkills.sh guide, https://qaskills.sh/blog/mutation-testing-stryker-guide-2026, and Microsoft Learn, https://learn.microsoft.com/en-us/dotnet/core/testing/mutation-testing, tool documentation (secondary/practitioner + official Microsoft doc).
- Practitioner survey of open-source mutation-testing users: developers report increased confidence in test suites and bug discovery as benefits, but performance/runtime cost was the most cited limitation (named by users of 6 of 10 tools studied, 17 of 36 total responses) — "Mutation Testing in Practice: Insights From Open-Source Software Developers," ResearchGate, https://www.researchgate.net/publication/379072181, peer-reviewed paper. Measured, denominator = 36 survey responses across 10 tools.
- Google's Test Certified program: a three-level rubric (later extended) that teams had to satisfy to be certified, developed by Google's Testing Grouplet starting ~2005–2006, with an internal goal that every team reach Level Three by end of 2009 — Mike Bland, "Test Certified," https://mike-bland.com/2011/10/18/test-certified.html, practitioner report from a Google insider (primary first-person account, not an official Google publication).

**Evidence quality.** Primary and measured for TestGen-LLM (peer-reviewed industry paper, exact figures with denominators, confirmed by re-fetching full text). Mutation-testing benefit/cost claims are corroborated by two independent sources (tool docs + a peer-reviewed practitioner survey) but the survey's benefit claims are self-reported, not outcome-measured. Test Certified is single-source (one insider's retrospective), not an official Google publication, so treat the internal deadline/level details as practitioner-report-level confidence.

**Transfer to an agent.** Directly transferable: the TestGen-LLM filter chain (build → pass reliably → increase coverage/kill mutants → human accept) is close to a ready-made S4/S5 rubric for "is this a real test," and its keep rates (roughly a quarter of generated candidates survive automated filtering; roughly three-quarters of what survives to human review gets accepted) give a baseline for what "good" looks like in an agent pipeline (FM-11). Proposed rubric line: a generated test fails S5 unless it (a) builds, (b) passes without flakiness across N reruns, and (c) either raises coverage or kills at least one mutant that the pre-existing suite missed.

**Gaps.** The discrepancy between the paper's abstract figure (11.5%) and its detailed table (196/1,979 ≈ 9.9%) was not resolved from the sources fetched — flagged rather than silently reconciled. Searched for Google's current (not 2005-era) test-quality certification practice and did not find a modern equivalent; Test Certified appears historical. No absolute counts (only percentages) were found for the 75%/57%/25% Reels/Stories filter results at the individual test-case level, only at the test-class level.

### RQ-S4-4. What published data exists on the quality of AI-authored code: defect rates, churn, duplication, and where agents fail most?

**Answer.** The published evidence is genuinely split by what is measured and who measures it: GitHub's own randomized trial found Copilot-assisted code scored higher on human-rated readability/reliability/maintainability, while GitClear's large-scale commit-history analysis found rising code churn and a multi-fold increase in duplicated code blocks over the same period AI tool adoption grew, and DORA's cross-industry survey found AI adoption correlated with a small code-quality gain alongside a larger software-delivery-stability loss. A newer, more targeted study (CodeThread) found that traditional static-complexity metrics (cyclomatic/cognitive complexity) do *not* significantly predict where agent-authored code causes downstream problems; what does predict failure is whether a later agent, building on top of prior agent-written code, encounters unannounced changes to input/output contracts — i.e., agents fail most at *extending* other agents' code correctly, not at writing initially-passing code. No single figure should be read as "the" AI code-quality number; each measures a different population, denominator, and time window.

**Patterns found.**
- GitHub randomized controlled trial: 202 valid developer submissions (104 with Copilot, 98 without, from 243 recruited, all with ≥5 years Python experience), plus a second blind-review phase with 25 reviewers producing 1,293 reviews. Results: Copilot-assisted developers 53.2% more likely to pass all 10 unit tests in the task; Copilot code rated +3.62% readability, +2.94% reliability, +2.47% maintainability, +4.16% conciseness; 13.6% more lines of code per code error found; reviewers 5% more likely to approve Copilot-assisted code — "Does GitHub Copilot improve code quality? Here's what the data says," GitHub Blog, https://github.blog/news-insights/research/does-github-copilot-improve-code-quality-heres-what-the-data-says/, company practice/research doc (vendor-authored, so treat quality claims as vendor-favorable — but the methodology is disclosed and the n is given).
- GitClear commit-history analysis across a large multi-company dataset (2020–2024, later extended into 2025/2026 data; one report cites 211 million changed lines analyzed): code churn (code re-touched within 2 weeks of authoring) rose from ~3.1% (2020) to 5.7% (2024) to a reported 7.1% (2025); duplicated code blocks per million changed lines rose from 40.3 (2023) to 73.0 (year-to-date at time of report), an 81% increase; refactored/moved code fell from ~25% of changed lines (2021) to under 10% (2024), while copy-pasted code overtook moved code for the first time in the dataset's history in 2024 — "AI Copilot Code Quality: 2025 Data Suggests 4x Growth in Code Clones" and "The Maintainability Gap: 2026 AI Code Quality Research," GitClear, https://www.gitclear.com/ai_assistant_code_quality_2025_research and https://www.gitclear.com/the_ai_code_quality_maintainability_gap, company/vendor research report (GitClear sells a code-quality product; treat as an interested party, though the underlying commit-mining methodology is disclosed). Measured, large denominator, but correlational — does not isolate AI authorship per commit from general trend.
- DORA 2024 State of DevOps: AI adoption correlated with a code-quality gain of +3.4% alongside a software-delivery-stability loss of -7.2%, described by secondary commentary as a "productivity-reliability paradox" — DORA / Google Cloud, https://dora.dev/research/2024/dora-report/, industry/lab research report (primary survey; exact wording of the +3.4%/-7.2% figures was relayed via secondary commentary and not independently re-verified against the primary PDF in this pass — see Gaps).
- CodeThread study: 1,377 filtered instances (from 1,687 originally) across four SWE benchmarks and 78 repositories. Traditional static maintainability metrics (cyclomatic complexity, cognitive complexity) were not statistically significant predictors (p>0.05) of whether a later agent successfully extended prior agent-written code. What did predict failure: input/error-contract (IEC) divergence between the original agent's code and what a later agent assumed, with an odds ratio of 1.83 (95% CI 1.15–2.92, p=0.011) for failure when such divergence was present. Downstream resolve-rate drops when extending agent-written code vs. human-written code reached up to 13.1 percentage points on one benchmark/model pair (GLM-4.7 on SWE-Bench Pro: 45.2% resolve rate extending human code vs 32.0% extending agent code); refactoring tasks showed the largest average drop (8.21 points), bug fixes the smallest (4.05 points) — "Is Agent Code Less Maintainable Than Human Code?", arXiv:2606.21804, https://arxiv.org/pdf/2606.21804, peer-reviewed/arXiv paper. Measured, denominators given per comparison.
- Independent (non-vendor) field study: Uplevel Data Labs reported developers with Copilot access saw a higher bug rate while issue throughput stayed flat — cited via secondary reporting, https://visualstudiomagazine.com/articles/2024/01/25/copilot-research.aspx, secondary commentary on a practitioner report (primary Uplevel report not independently fetched in this pass).

**Evidence quality.** Multiple independent sources, but they disagree in direction and each has a plausible interest or measurement limitation: GitHub's study is vendor-authored but methodologically transparent (n disclosed, RCT design); GitClear is a vendor with a directly competing commercial interest in "AI code is worse" framing, though its churn/duplication metrics are drawn from mined commit history, not opinion; DORA is the most neutral single source but its exact figures here are relayed secondhand; CodeThread is the newest and most methodologically pointed (isolates a specific causal mechanism — contract drift — rather than a blanket "AI code is worse/better" claim) but is a single not-yet-widely-replicated arXiv paper. Overall: measured, large-sample, but not converging on one number — the honest summary is "more churn and duplication in the aggregate commit-history record since AI-tool adoption grew, alongside mixed human-rated micro-quality results, and a newer signal that the specific failure mode is contract drift when agents build on agent code."

**Transfer to an agent.** The CodeThread contract-drift finding is the most actionable: it implies S3/S4 should require an agent to explicitly declare and preserve the input/output contracts of any code it touches, and S5 should specifically diff contracts (function signatures, error types, side effects) against what the plan declared, rather than relying on complexity metrics as a maintainability proxy (FM-01, FM-03, FM-11). Proposed rubric line: a change fails S5 if it alters an input/error contract of touched code without that alteration being named as a decision in the S3 plan.

**Gaps.** Did not independently re-verify the DORA 2024 +3.4%/-7.2% figures against the primary DORA report PDF (relied on secondary summaries after search results did not surface the exact wording in the primary document); flagged rather than presented as fully primary-verified. Did not find a Google- or Microsoft-internal published defect-rate figure specifically for AI-authored code in first-party production systems (searched directly; only third-party/vendor studies surfaced) — this is a real gap, not filled with a generality.

### RQ-S4-5. How do organisations prevent silent decisions during implementation, such as unlogged deviations or invented behaviour?

**Answer.** No published, named industry practice was found that maps cleanly onto "agent logs its own deviations from an approved plan during implementation" — this is a genuine gap. What exists are adjacent, more general mechanisms that the same problem statement borrows from: deviation logs in regulated/protocol-driven fields (clinical research, project management) that record what changed, why, and whether it was authorized; conformance-analysis research on the general software-engineering problem of implementations drifting from their design over time; and a small number of emerging, practitioner-built (not lab-published) tools that add automated "did the agent stay in scope" gates to agentic coding workflows. No primary source was found describing a lab or major engineering org's specific policy for LLM-agent deviation logging.

**Patterns found.**
- Deviation logs as a general control pattern: a predefined template records each deviation, its cause, and whether it was authorized, to keep the record comparable across incidents — Office for the Protection of Research Subjects deviation-log template, https://oprs.research.illinois.edu/forms/deviation-log-template, and ProjectManagement.com deviation-log template, https://www.projectmanagement.com/deliverables/327625/deviation-log-template, practice docs (from clinical-research and project-management domains, not software engineering specifically — analogy, not direct evidence).
- Conformance analysis as a named software-engineering research problem: implementations are known to drift from their design over time ("architectural erosion," "concept drift"), and conformance analysis is the general technique for detecting divergence between two system artifacts (e.g., design vs. implementation) — "In Specs we Trust? Conformance-Analysis of Implementation to Specifications in Node-RED," arXiv:2502.09117, https://arxiv.org/pdf/2502.09117, peer-reviewed paper. This names the problem class but is about IoT flow specifications, not LLM-agent plans specifically.
- Emerging practitioner tooling: "agent-guardrails," an open-source merge-gate project, explicitly checks that AI-agent changes match declared expectations before merge, including a scope-validation gate ("AI only touches allowed files") with configurable severity (error blocks merge, warning allows an acknowledged violation) — https://github.com/logi-cmd/agent-guardrails, practitioner/open-source project (not a lab or major-vendor publication; unverified adoption or precision data).
- Indirect evidence that silent scope/behavior deviation is a live problem in agent-authored PRs: "oversized PR" and "experimentation-only" are documented agent-specific PR rejection categories not seen (or seen far less) in human PRs — "Why Agentic-PRs Get Rejected," arXiv:2602.04226, https://arxiv.org/html/2602.04226v1, peer-reviewed paper (same source as RQ-S4-1). Measured, denominators given there.

**Evidence quality.** Weak/adjacent. The deviation-log pattern is well-established but borrowed from other regulated domains, not software or AI-agent engineering. The conformance-analysis research names the right problem but not in an LLM-agent context. The one directly relevant tool (agent-guardrails) is an unvetted open-source project with no published precision or adoption data. This question is best answered honestly as a gap with adjacent analogues, per the rules for answering.

**Transfer to an agent.** The analogy transfers as a structural pattern even without direct software-engineering precedent: require S4 output to include a structured deviation record (each deviation from the S3 plan, its cause, and whether it was a judgment call or an error) modeled on the clinical/PM deviation-log template, gated the same way agent-guardrails gates file scope. Proposed pipeline rule: S4 is not complete until the agent emits a deviations list (possibly empty) in a fixed schema — file/decision, plan said, agent did, why — consumed directly by the S5 rubric and the S6 review packet (P4, P9).

**Gaps.** Searched directly for "deviation log agent plan implementation," "self-report conformance PR template," and "ADR update on deviation from decision" in a software-engineering-specific context; found only cross-domain analogues and one unverified open-source tool. No published evidence found of a lab (Anthropic, OpenAI) or major engineering org (Google, Meta, Uber) documenting a specific practice for logging agent deviations from an approved plan during implementation.

### RQ-S5-1. What automated or LLM-based gates exist for detecting low-value tests, redundant comments, dead code, and style drift, and what is known about their precision?

**Answer.** Each of the four target categories has at least one class of tool, but precision evidence is uneven and mostly comes from small academic studies or practitioner blog comparisons rather than large industry-reported figures. Test-smell detectors (rule-based tools like TsDetect/PyNose) have historically reported high precision/recall on common smells but degrade on rare smells and are increasingly being supplemented or replaced by LLM-based detectors, which themselves show a recall problem (missing real smells) more than a precision problem. Dead-code detectors are dominated by false positives from framework "magic" (Django/Flask/pytest-style implicit usage), with one head-to-head practitioner comparison finding roughly 3x fewer false positives from a framework-aware tool than a purely syntactic one. Redundant-comment and style-drift detection remain the least mature of the four: existing lints only catch a narrow proxy (commented-out code), not semantic redundancy or drift, and current research explicitly recommends hybrid static+LLM pipelines rather than trusting either alone.

**Patterns found.**
- Rule-based test-smell detectors (PyNose for Python, TsDetect for Java) report high precision and recall for common, high-prevalence smells, but for low-prevalence smells recall becomes statistically unreliable, so evaluation shifts to a precision-only protocol — one study reported zero false positives among all audited alerts for its lowest-prevalence smells under that protocol — "A Road to Find Them All: Towards an Agnostic Strategy for Test Smell Detection" and related work summarized via https://www.emergentmind.com/topics/test-smell-detection-tools, secondary synthesis of peer-reviewed work.
- LLM-based test-smell/code-smell detection (GPT-4 and DeepSeek-V3 compared): both models "struggle with recall," missing real smells more than they falsely flag clean code — "Benchmarking LLM for Code Smells Detection: OpenAI GPT-4.0 vs DeepSeek-V3," ACM/ESEM, https://dl.acm.org/doi/10.1145/3756681.3756993, peer-reviewed paper. Direction of error (recall, not precision) is the notable finding.
- Recommended remedy in the literature is hybrid pipelines (static + metric + LLM) to maximize precision, recall, and interpretability for CI/CD deployment — synthesis across the code-smell papers surfaced (arXiv:2605.22976, arXiv:2512.18020), peer-reviewed papers.
- Dead-code / unused-code static analysis: syntactic tools (e.g., Vulture for Python) assign a confidence score (60–100%) per finding because false positives are common, especially from framework-implicit usage (Django/Flask/FastAPI/pytest patterns that look unused statically but run at runtime); a framework-aware tool (Skylos) found 7 more true dead-code items than Vulture on Flask while producing roughly 3x fewer false positives (Vulture: 260 false positives on Flask) — "Python Dead Code: I Scanned Flask, FastAPI, and 7 Other Popular Repos," DEV Community, https://dev.to/duriantaco/python-dead-code-i-scanned-flask-fastapi-and-7-other-popular-repos-heres-what-i-found-5c1c, practitioner report (single-author blog comparison, not a peer-reviewed study — treat as anecdotal-but-quantified).
- Redundant-comment / commented-out-code lint: SonarQube S125 flags comment blocks that look like code, with community-reported false positives on ordinary comments containing code-like punctuation (e.g., trailing semicolons) — https://community.sonarsource.com/t/semi-colons-in-comments-detected-as-commented-out-code/60414, tool community report. No published precision figure; this rule also does not address semantic redundancy (a comment that accurately but uselessly restates the adjacent line), only literal commented-out code.
- Style drift: no dedicated "style drift" detector or published precision figure was found distinct from ordinary linters (ESLint, Pylint, SonarQube rule sets), which enforce fixed style rules rather than detecting drift from a codebase's own established (unwritten) conventions.

**Evidence quality.** Mixed and mostly secondary/practitioner-level rather than large-scale industry-measured. Test-smell precision/recall claims come from peer-reviewed academic studies but on limited benchmarks. Dead-code false-positive comparison is a single practitioner blog post, not peer-reviewed. No source at all was found for a mechanically measured "redundant comment" precision figure or a "style drift" detector with published precision — these are real gaps.

**Transfer to an agent.** Transfers as a design constraint rather than a ready rubric: none of these four gate categories should be trusted as a sole automated pass/fail at S5 given the recall gaps (test/code smells) and precision gaps (dead code, commented-out code) found; the literature's own recommendation — hybrid static+LLM with a human or second-agent spot-check — matches the charter's S5 design (a second independent agent pass, P6). Proposed rubric line: S5 gates flag candidates for removal/rewrite but do not auto-remove; a flagged item requires either a second-pass agent confirmation or is surfaced in the review packet as a declared blind spot (P7) if the gate's known false-positive mode (framework-implicit usage, code-like comments) applies.

**Gaps.** Searched specifically for a published precision/recall figure for LLM-based redundant-comment detection and for a named "style drift" detector; neither was found. Searched for large-scale (not single-blog-post) dead-code false-positive rates in industry codebases; not found beyond the one practitioner comparison cited above.

### RQ-S5-2. What presubmit and pre-merge checks do organisations with critical systems run, and how do they split cheap checks from expensive ones?

**Answer.** The consistent pattern across Google, Uber, and Meta is a two-tier (sometimes three-tier) system: a fast, high-confidence presubmit tier gates the merge/submit action itself and is deliberately restricted to hermetic, fast, reliable tests, while slower, flakier, or more resource-intensive tests run post-submit on a continuous build and are not allowed to block individual changes. Google's TAP is the most concretely documented: presubmit is scoped to fast unit tests, and passing presubmit is reported to correlate with a 95%+ likelihood of passing the full (including post-submit) test suite, which is the empirical justification for not running everything pre-merge. Merge itself is additionally gated by a speculative merge-queue layer (Uber's SubmitQueue) that validates multiple pending changes in parallel against predicted future states of the trunk, rather than one at a time, to keep the tier-1 gate both fast and consistent.

**Patterns found.**
- Google TAP (presubmit) scoped to fast, reliable tests (typically project unit tests); large, nonhermetic, flaky, or resource-intensive tests are explicitly excluded from presubmit and instead run on a separate post-submit continuous build; passing presubmit correlates with 95%+ likelihood of passing the rest of the test suite — *Software Engineering at Google*, ch. 23 ("Continuous Integration"), https://abseil.io/resources/swe-book/html/ch23.html, and Google research paper "The State of Continuous Integration Testing @Google," https://research.google.com/pubs/archive/45880.pdf, company practice doc + peer-reviewed/industry paper. The 95%+ figure is stated as a measured correlation but the underlying study's sample was not independently re-verified in this pass.
- Uber SubmitQueue: a speculative merge queue that rebases and validates multiple pending changes in parallel against predicted future trunk states rather than sequentially; used by 4,500+ engineers, processing tens of thousands of changes/month across six monorepos and seven languages; isolates and retries around failing changes automatically, without human intervention — Uber Engineering, "Slashing CI Costs at Uber," https://www.uber.com/ca/en/blog/slashing-ci-costs-at-uber/, and the open-sourced project README, https://github.com/uber/submitqueue, company practice doc + open-source project doc. Measured (engineer count, monthly volume), but not broken down into a cheap/expensive test-tier split as explicitly as Google's account.
- Meta Sandcastle: internal CI integrated with Phabricator, with a stated CI stack of three layers — builds, static analysis, and testing — and a top-line goal of developer efficiency (minimizing wait time on diffs) rather than exhaustiveness per commit — secondary conference/blog coverage, https://atscaleconference.com/videos/the-journey-of-turning-a-ci-system-into-a-universal-platform/ and https://compiledexperience.com/blog/posts/integrating-sandcastle-into-your-builds, secondary/practitioner sources (no official Meta engineering blog post on Sandcastle's tiering was located directly — see Gaps).
- Netflix: general confirmation that Netflix runs continuous, frequent deployment with automated testing (unit, integration, load, canary) and that its product-integration-test team's explicit charter is not to impede velocity while remaining a quality gate, but no source found with an explicit cheap/expensive tier split comparable to Google's TAP account — Netflix TechBlog, "Product Integration Testing at the Speed of Netflix," https://medium.com/netflix-techblog/product-integration-testing-at-the-speed-of-netflix-72e4117734a7, company practice doc (directionally relevant, not tier-specific).

**Evidence quality.** Primary and reasonably well corroborated for Google (a book by Google engineers plus a Google research paper) and Uber (company engineering blog plus an open-sourced, inspectable codebase). Meta and Netflix evidence is weaker — secondary/conference coverage rather than a first-party engineering-blog account with the same level of tiering detail as Google's.

**Transfer to an agent.** Transfers directly as a two-tier design for S5/S6: a fast, hermetic tier (lint, unit tests, the S5 slop-rubric checks) gates before a human ever sees the change, while expensive tests (integration, mutation testing, LLM-judge passes) run asynchronously and are not allowed to block the human review queue, mirroring Google's presubmit/post-submit split (S5 exit criterion). Proposed rubric line: S5's automated gates are split into a blocking tier (must pass before S6 review packet is generated) and an advisory tier (runs in parallel, surfaces findings into the review packet without blocking it), matching the "95% predictive of full suite" pattern rather than requiring full expensive-check completion before every human touchpoint.

**Gaps.** Searched specifically for a first-party Meta engineering blog post on Sandcastle's cheap/expensive test tiering and a first-party Netflix post with an explicit tier split; neither was found — relied on secondary/conference coverage for Meta and a directionally relevant but non-tier-specific Netflix post.

### RQ-S5-3. What is known about using an LLM as a reviewer or judge of code and plans against a rubric: calibration to human judgment, self-preference bias, independence from the authoring model?

**Answer.** LLM-as-judge is an active, fast-moving research area with three consistent findings relevant here: judges reliably favor their own model family's outputs (self-preference bias), judges are highly sensitive to surface features unrelated to correctness (position in the prompt, verbosity, an "authority" framing, a "this is a refined version" cue) with effect sizes large enough to flip a judgment from near-certain-correct to near-certain-wrong, and calibration to human judgment requires a deliberate measurement step (sampling real cases, having multiple humans label them, then checking judge-human agreement) rather than being assumed. A code-review-specific study found the same bias patterns hold for code generation, code repair, and test generation judging tasks specifically, and that cross-family judging (using a judge from a different model family than the one that authored the code) is a proposed mitigation, though this introduces a cost/latency tradeoff with no human analog.

**Patterns found.**
- Self-preference bias: judges favor outputs in their own style, most pronounced when judge and generator share a model family or when the judge is a newer version of an older one — "Self-Preference Bias in LLM-as-a-Judge," https://www.researchgate.net/publication/385353198, peer-reviewed paper (accessed via abstract/secondary summary, not full text).
- Code-review-specific bias study: across code generation, code repair, and test-generation judging tasks, authority/refinement framing pushed judges toward near-ceiling accuracy (>85%) when the favored answer was actually correct but collapsed to near-floor (<20%) when it was not — a 60+ percentage-point swing driven by framing alone, not correctness; verbosity bias pushed judgments in the opposite direction of authority framing; on test-generation specifically, a "distraction" manipulation dropped GPT accuracy from 77.46% to 62.51% (a 14.95-point drop) — "Bias in the Loop: Auditing LLM-as-a-Judge for Software Engineering," arXiv:2604.16790, https://arxiv.org/html/2604.16790v1, peer-reviewed/arXiv paper. Measured, uses CodeJudgeBench's execution-verified gold labels as ground truth (not human agreement directly — see Evidence quality).
- Calibration methodology: recommended practice is to sample 100–300 real cases, have 2–3 human annotators label them on the target rubric, compute inter-annotator agreement (Cohen's kappa; >0.6 acceptable, >0.8 strong), then score the same cases with the LLM judge and compute judge-human agreement on the same scale; kappa below 0.5 signals the rubric/prompt needs rework — Deepchecks, "What Is LLM-as-a-Judge Calibration?", https://deepchecks.com/llm-judge-calibration-automated-issues/, secondary/vendor practice doc (not independently peer-reviewed, but the kappa-based method is standard inter-rater-reliability practice from measurement literature generally).
- Mitigation: cross-family judging (judge from a different model family than the generator) is proposed to reduce self-preference bias, described as a bias class with no human-review analog — synthesis across the self-preference and bias-in-the-loop sources above.

**Evidence quality.** Primary, peer-reviewed for the bias effect sizes (Bias in the Loop paper gives concrete percentage swings with a defined ground truth). However, the ground truth used in that paper is execution-based test verification, not direct human-judgment agreement, so it measures "does bias make the judge diverge from an objectively correct answer" rather than "does the judge's score match what a human reviewer would say" — a real distinction for a rubric that grades subjective qualities (plans, not just pass/fail code). The calibration-methodology source is a vendor blog, not a peer-reviewed study, though its method (kappa-based inter-rater reliability) is standard practice from the wider measurement literature.

**Evidence quality note:** two independent primary/near-primary sources (the self-preference paper and the Bias-in-the-Loop paper) agree on the core self-preference and framing-sensitivity findings.

**Transfer to an agent.** Transfers directly and is high-priority given the charter's reliance on rubric-graded automated passes (P2) at S5 and S6: an LLM judge used in S5's cleanup pass or any future rubric-scoring step should not be the same model family that authored the implementation, and any rubric-grading gate should be calibrated against a human-labeled sample before being trusted, with kappa reported. Proposed rubric line: S5/S6 automated judging is disqualified from self-grading (the model that wrote the code or plan may not also score it against the rubric), and any LLM-judge gate must report its calibration kappa against a human-labeled sample before being used as a blocking gate.

**Gaps.** Searched for a code-review-specific (not general-purpose) study that directly measures LLM-judge agreement against human reviewer scores (rather than against execution-verified ground truth); did not find one with reported kappa/agreement figures for code or plan review specifically — this is a partial gap worth flagging to RQ-X-5 (rubric calibration), which likely covers the same territory from the grading-methodology side.

### RQ-S5-4. How can a change be checked for staying within its declared scope, meaning the files, modules, and services named in the plan?

**Answer.** This is the weakest-evidenced question in the packet: there is no published, measured industry practice for checking an agent's (or a human's) change against a declared file/module scope from a plan. What exists is mechanical infrastructure that makes such a check possible (CI can trivially enumerate the files changed in a PR) and a small number of emerging, not-yet-validated, open-source guardrail tools purpose-built for agentic coding that implement exactly this check as a merge gate. No lab or major engineering org publication describing this as a named, measured practice was found.

**Patterns found.**
- Mechanical building block: CI systems (e.g., GitHub Actions) can enumerate the files modified in a PR as a standard step, which is the prerequisite primitive for any scope check — "Get Files Modified in a PR in GitHub Actions," Baeldung, https://www.baeldung.com/ops/github-actions-pr-files-modified, practitioner/tool documentation. Infrastructure, not a scope-checking practice itself.
- Purpose-built agent scope gate: "agent-guardrails," an open-source merge gate for AI-generated code, explicitly validates that "AI only touches allowed files," with configurable severity (error blocks merge; warning allows an acknowledged violation), and is built to work with Claude Code, Cursor, Codex, and Gemini specifically — https://github.com/logi-cmd/agent-guardrails, practitioner/open-source project. No adoption numbers, precision data, or case studies found; this is a nascent tool, not an established practice.
- Cursor's built-in access control: agents can be blocked from touching specific files via a `.cursorignore` file, and agent file writes outside configuration files generally do not require per-file approval by default — Cursor documentation, "Agent Security," https://cursor.com/docs/agent/security, official lab/tool documentation. This is an allow/deny file list set in advance, not a dynamic check against a plan's declared scope for a specific change.
- Recommended production pattern (practitioner write-up, not measured): explicitly define in-scope files (agent may inspect/edit) and out-of-scope files (agent must not modify) per task — "AI Coding Agent Guardrails: Production Workflow for Cursor, Claude Code, and Codex," https://www.mouhssinelakhili.com/en/blog/ai-coding-agent-guardrails-production-workflow, practitioner report.

**Evidence quality.** Weak. All sources are either generic CI infrastructure documentation, official but general-purpose access-control documentation (not scope-vs-plan checking specifically), or small/unverified open-source tooling and practitioner blog posts. No peer-reviewed, lab-published, or major-company-published source measures scope-conformance checking as a named practice with any precision or adoption figure.

**Transfer to an agent.** The pattern still transfers as a mechanically simple, high-value check even without strong published precedent: since S3's plan already names "code to touch and code deliberately not touched" (per the charter's stage map), S5 can diff the actual changed-file list against that declared list with zero LLM involvement — this is the cheapest, highest-precision gate in the whole pipeline because it's a literal set-difference, not a judgment call. Proposed rubric line: S5 fails automatically (not just flags) any change touching a file or service not named in the S3 plan's scope section, unless the plan explicitly reserved discretion for that path; this directly operationalizes FM-05 (scope creep) as a mechanical, not judgment-based, gate.

**Gaps.** Searched specifically for a published measurement of scope-check precision/false-positive rate, and for any lab (Anthropic, OpenAI) or major engineering org (Google, Meta, Uber) documentation of scope-vs-plan enforcement as a named CI practice; none found. No published evidence found for this question beyond generic infrastructure and small unverified open-source tooling — flagged rather than filled with a plausible generality.
