### RQ-S7-1. How do organisations size a canary or flag-ramp verification window and define automatic kill conditions from SLOs?

**Answer.** Organisations size canary/ramp windows relative to release cadence and traffic volume rather than a fixed clock duration: Google's guidance is that the window must be large and long enough for the sample to be representative, scaled so that daily-release teams run short canaries and weekly-release teams can afford longer ones, judged against a small, stack-ranked set of SLI-derived metrics (recommended at "no more than a dozen"). Kill conditions are expressed as per-metric thresholds against a control/baseline population: Kayenta (Netflix/Spinnaker) scores each configured metric and lets any metric be marked "critical," failing the whole canary with a score of zero if that metric's ratio exceeds a configured increase/decrease multiplier. LaunchDarkly's guarded rollouts apply the same idea to flag ramps — staged percentages (commonly 1/10/50/100%, no single step over 50%), sequential statistical testing on each guardrail metric, and automatic pause or rollback when a metric's confidence interval falls entirely on the "worse" side, or when a stage doesn't reach a minimum number of evaluating contexts.

**Patterns found.**
- Window length scaled to release cadence and traffic volume, not a fixed duration; evaluate a stack-ranked set of SLI-derived metrics ("no more than a dozen") — Google SRE Workbook, "Canarying Releases," https://sre.google/workbook/canarying-releases/, company practice book (primary).
- Per-metric "critical" flag fails the entire canary (score = 0) on breach of a configured mean-ratio threshold; non-critical metrics contribute to an aggregate score — Kayenta docs, "canary-config.md," https://github.com/spinnaker/kayenta/blob/master/docs/canary-config.md, official tool documentation (primary).
- Staged percentage ramps (e.g. 1/10/50/100%, no stage over 50% of traffic) with sequential testing per guardrail metric and automatic pause/rollback when the confidence interval sits entirely on the worse side of zero — LaunchDarkly, "Guarded rollouts," https://launchdarkly.com/docs/home/releases/guarded-rollouts, official tool documentation (primary).
- Automatic rollback also triggers when a stage does not reach a minimum number of evaluating contexts (undersized sample), independent of metric regression — same source.
- Kayenta computes an aggregate canary score from grouped metrics and can auto-promote, auto-fail, or route to human approval — Netflix TechBlog, "Automated Canary Analysis at Netflix with Kayenta" (page returned HTTP 403 on direct fetch; claim drawn from search-engine summary of the post and secondary coverage in SD Times, "Google and Netflix introduce open-source automated canary analysis service," https://sdtimes.com/os/google-and-netflix-introduce-open-source-automated-canary-analysis-service/ — say so), company engineering blog (accessed via snippet, not directly read).

**Evidence quality.** Primary and convergent: three independent official sources (Google SRE Workbook, Kayenta's own docs, LaunchDarkly's own docs) agree on the same two mechanisms — a sizing heuristic tied to cadence/traffic, and a per-metric threshold or statistical-significance rule as the kill condition. No source gives a closed-form numeric formula (e.g. a sample-size calculation) for window duration; all frame duration as dependent on metric variance and release cadence. The Netflix Kayenta blog itself was inaccessible (403), so that one claim rests on a secondary summary rather than a direct read.

**Transfer to an agent.** Applies directly to S7. Rubric line: the rollout plan must state one ramp schedule (stages/percentages or cohorts) sized to the ticket's expected traffic volume and the service's release cadence, plus a named set of no more than a dozen SLI-derived guardrail metrics — each expressed as a Grafana query with an explicit critical-fail threshold — before the plan can pass the S7 gate.

**Gaps.** Searched for a documented Meta continuous-deployment canary/kill-condition policy; found only unsourced secondary summaries describing an internal-then-2%-then-100% pattern with feature-flag kill switches (Gatekeeper), with no verifiable primary Meta engineering blog link, so it is not cited as evidence. No source gave a concrete recommended minimum window duration in minutes or hours.

### RQ-S7-2. What is published practice for automated rollback, and for deciding between rollback and fix-forward?

**Answer.** The dominant published pattern (Google) is "detect, roll back, fix, then roll forward" rather than patching a live problem in place: once a fault is reasonably suspected to be in a recent release, the recommended default is to roll back first and diagnose second, because fixing under incident pressure with a partially understood bug is itself error-prone and risks compounding the outage. This default is explicitly conditioned on rollback being cheap to execute: it requires frequent, small, predictable releases so any one rollback reverts little; automated, pre-tested rollback mechanisms exercised via scheduled "just because" rollback drills rather than first tried during a live incident; and a release-sequencing discipline for schema/data changes — ship a schema-compatible no-op binary (v+1) before the migration and the feature binary (v+2) after, so a single-step rollback never leaves a binary running against an incompatible schema. Fix-forward is the fallback only when rollback itself is shown to be unsafe or already broken.

**Patterns found.**
- "Roll back, fix, roll forward" as the preferred default; rolling forward under pressure treated as more error-prone than rollback — Google Cloud Blog, "Reliable releases and rollbacks (CRE life lessons)," https://cloud.google.com/blog/products/gcp/reliable-releases-and-rollbacks-cre-life-lessons/, company practice doc (primary).
- Precondition: frequent, small releases so the blast radius (and cost) of any one rollback stays low — same source.
- Three-stage release sequencing (v, v+1 schema-compatible no-op, v+2 feature) so a schema migration never blocks rollback — same source.
- Scheduled rollback drills between incidents, to surface broken/incompatible rollback paths outside of a live fire — same source.
- Rollback is a standard SRE mitigation, but untested rollback procedures were "flawed" and lengthened a real outage, leading to a requirement that rollback procedures be tested before large-scale changes — Google SRE Book, "Emergency Response," https://sre.google/sre-book/emergency-response/, company practice book (primary).

**Evidence quality.** Primary but single-organisation: both sources are Google's own publications (a Cloud/CRE blog and the SRE book), with one real internal incident cited as the evidence for "test your rollback procedures." This is one converging institutional voice, not independent corroboration from a second company, and the underlying claim is doctrinal/anecdotal rather than a measured comparison of rollback vs. fix-forward outcomes across many incidents.

**Transfer to an agent.** Applies directly and maps onto the S7 exit criterion ("verification window passed with no kill condition triggered"). Rubric line: the rollout plan's default response to any kill-condition trigger is rollback; choosing fix-forward instead requires an explicit, named reason rollback is unsafe (e.g. an in-flight, incompatible schema migration) plus human sign-off before it can be selected.

**Gaps.** Searched for a second company's published rollback-vs-fix-forward decision framework and for measured data (e.g. MTTR difference between the two strategies); found only vendor/consultancy listicles (Aviator, Octopus, Medium-hosted posts) with no named organisation, no measured figures, and no clear primary-source status, so they were excluded per the sourcing rule. No published evidence found comparing outcomes of the two strategies quantitatively.

### RQ-S7-3. How do organisations manage feature flag lifecycle and debt, and how is flag cleanup planned at design time?

**Answer.** Mature practice treats a flag's removal as a deliverable created alongside the flag itself, not an afterthought: LaunchDarkly's own guidance is to open the cleanup pull request in parallel with the feature pull request — the removal diff already exists and only needs merging once rollout completes — and to require every flag to carry an owner, a purpose description with a last-reviewed date, and a temporary/permanent classification. On the tooling side, Uber's Piranha treats a flag left unmodified in the flag-management system past a per-team staleness threshold (Uber's example: 8 weeks) as a cleanup candidate, then uses AST analysis to mechanically delete the dead branch and opens a diff for a human to merge; Uber reports using it to remove roughly two thousand stale flags, with diff generation taking under three minutes. LaunchDarkly separately publishes a numeric health benchmark — a 90–120 day time-to-archive target and a high archived-to-unarchived flag ratio — as the debt signal teams should track.

**Patterns found.**
- Cleanup PR authored alongside the feature PR at flag-creation time, containing only the flag-removal diff, ready to merge once rollout completes — LaunchDarkly, "Reducing technical debt from feature flags," https://launchdarkly.com/docs/guides/flags/technical-debt, official practice doc (primary).
- Every flag assigned an owner, a description tracking last-reviewed date and purpose, and a temporary-vs-permanent classification — same source.
- Numeric health targets: 90–120 days as a "healthy" time-to-archive benchmark; a high archived-to-unarchived ratio as the debt signal — same source.
- Staleness defined operationally as "unmodified in the flag system for more than N weeks" (team-configurable; Uber's stated example is 8 weeks), triggering an automated AST-based diff that deletes the dead code branch — Uber Engineering Blog, "Introducing Piranha: An Open Source Tool to Automatically Delete Stale Code," https://www.uber.com/en-IT/blog/piranha/, company engineering blog (primary). Uber reports removing "around two thousand" stale flags, with diff generation in "less than 3 minutes."
- A peer-reviewed evaluation of the same tool reports the generated diffs were mostly low-risk: of 1,381 flags processed (17% of the flag population studied), 65% of generated diffs landed with no further changes and over 85% compiled and passed tests — Ramanathan et al., "Piranha: Reducing Feature Flag Debt at Uber," ICSE 2020 Software Engineering in Practice, https://manu.sridharan.net/files/ICSE20-SEIP-Piranha.pdf, peer-reviewed industry paper. The PDF could not be parsed by available tooling in this environment; these figures are drawn from a search-engine summary of the paper's results rather than a direct read — flagged as lower-confidence than the other findings in this answer.

**Evidence quality.** Two independent primary organisational sources (Uber's own engineering blog, LaunchDarkly's own docs) converge on "plan removal at flag-creation time" and "use an age-based staleness signal with an owner and a review date." The specific landing/compile-rate percentages for Piranha come from a peer-reviewed paper but were accessed only via a search-engine snippet, not a direct read of the source PDF, and are noted at reduced confidence accordingly.

**Transfer to an agent.** Applies directly; it also serves FM-04 (tech debt silently fixed or never surfaced), not just S7. Rubric line: any plan that introduces a rollout flag must state the flag's expected life (temporary vs. permanent), its owner, and — for temporary flags — the removal condition plus a placeholder cleanup diff, checked for staleness on a fixed interval (e.g. 8–12 weeks after full rollout).

**Gaps.** Searched specifically for Google's internal flag-lifecycle practice (named alongside LaunchDarkly and Piranha in the charter's research agenda); found no distinct published Google document on flag debt beyond passing secondary references to Gatekeeper-style systems, so no Google-specific claim is included.

### RQ-S7-4. When logs are the primary verification signal and automation cannot read them, how do teams structure human verification steps and checklists after deploy?

**Answer.** Published evidence for this exact practice — a named human step that reads logs specifically because automation cannot — is thin. Most company engineering writing frames post-deploy verification around dashboards and metrics, which are the automatable signal, and treats logs as the tool reached for only after a metric or a person's suspicion has already flagged a problem, not as a routinely scheduled checklist item in its own right. Two adjacent, better-documented patterns are transferable even though neither is written as "log verification because automation can't see logs": Google's monitoring philosophy deliberately keeps log collection/analysis as a separate concern from its core metrics-plus-dashboards-plus-alerting stack, implying logs are reserved for ad hoc, human-driven investigation rather than routine automated verification; and GitHub's ChatOps practice converts what would otherwise be a vague "go check the logs" instruction into named, discoverable, pre-built commands that run canned queries against the log backend, so the human's job becomes picking from a known menu of checks rather than free-form log reading.

**Patterns found.**
- Logs deliberately kept as a separate concern from the automated metrics/dashboard/alerting stack, which is described as working well "as a relatively standalone system" on its own — implying logs are for ad hoc investigation, not routine automated verification — Google SRE Book, "Monitoring Distributed Systems," https://sre.google/sre-book/monitoring-distributed-systems/, company practice book (primary).
- Google's own pre-launch checklist chapter covers reliability, monitoring, and capacity questions in depth but does not itemise a post-launch human log-review step — Google SRE Book, "The Launch Coordination Checklist," https://sre.google/sre-book/launch-checklist/, company practice book (primary). Included as a directly relevant negative finding.
- On-call investigations repeat "the same things... with common investigation... steps," which are codified as named, discoverable ChatOps commands (e.g. a `.actions check` command family) running pre-built queries against Splunk/Kusto — turning ad hoc log-reading into a menu of runnable, named checks — GitHub Blog, "Using ChatOps to help Actions on-call engineers," https://github.blog/engineering/infrastructure/using-chatops-to-help-actions-on-call-engineers/, company engineering blog (primary). The post's subject is incident response, not deploy verification specifically; transfer here is by analogy, not direct statement.
- Continuous-deployment culture at Etsy pairs every push with an engineer "watching the wall" of dashboards immediately after deploy for spikes or valleys — Etsy Engineering, "Quantum of Deployment" (direct fetch returned HTTP 403; claim drawn from search-engine summary and corroborating secondary coverage, CIO.com, "Continuous Deployment Done In Unique Fashion at Etsy.com," https://www.cio.com/article/284292/developer-continuous-deployment-done-in-unique-fashion-at-etsy-com.html — say so), company engineering blog (accessed via snippet, not directly read).
- General runbook-authoring guidance converges on replacing a bare "check the logs" instruction with a named log source and a named error pattern to look for — multiple practitioner/vendor runbook guides (e.g. Rootly, "Incident Response Runbooks"; OpsBrief, "Incident Response Runbooks"), secondary sources, not tied to one named company's measured practice.

**Evidence quality.** Weak, as anticipated by the question. No primary source publishes a structured, named checklist for human log verification specifically because automation cannot reach the logs. What was found is: (a) one directly relevant negative finding — Google's own launch checklist does not contain this item; (b) one well-documented, directly transferable mechanism (canned/named log queries via ChatOps) whose source article is about incident response rather than deploy verification; and (c) generic, multi-source but low-individual-authority practitioner advice about runbook wording.

**Transfer to an agent.** Applies as a design pattern to borrow, not a practice to copy wholesale — consistent with the charter's declared blind spot (OpenSearch has no agent access; P7). Rubric line: the S7 human log-verification step must name the exact query to run (index, time window, field filters) and the exact pass/fail pattern, never a bare instruction to "check the logs"; any query used more than once is saved as a named, reusable check rather than re-specified per ticket.

**Gaps.** Searched directly for "post-deploy log verification checklist," "manual log review after deploy," and named-company examples (Etsy, GitHub, Shopify, Stripe); found dashboard-centric and incident-response-centric material but no company-published checklist whose explicit subject is what a human should read in logs after a deploy, given that automation cannot. Etsy's own blog post could not be fetched directly (blocked); this is recorded as a genuine gap in published evidence, not filled with a plausible generality.

### RQ-S7-5. How do organisations with critical systems balance change control formality (change windows, approvals) against deployment frequency?

**Answer.** The clearest measured finding is DORA's: heavyweight, external (change-manager or CAB) approval processes applied to every change are negatively correlated with deployment frequency, lead time, and time-to-restore, and show no measurable correlation with change failure rate — meaning the formality buys no stability while it costs speed; organisations with such a process in place were reported 2.6 times more likely to be classified low performers in DORA's own performance tiers. DORA's recommended reconciliation, echoed in ITIL 4's later "change enablement" revision, is to reserve individual formal approval for genuinely high-risk changes, treat most changes as pre-authorised "standard changes" whose approval authority is a passed CI/CD pipeline (automated tests, policy checks) rather than a standing committee, and use peer review captured in the same platform as the change to satisfy segregation-of-duties requirements, repositioning the CAB toward cross-team coordination and high-level trade-off decisions. In practice, teams vary in how literally they apply this: some replace calendar-based freezes with engineering controls (flags plus fast rollback/roll-forward) year-round, others keep narrow, selectively scoped freezes (e.g. only for native-mobile release trains, or a short, bounded window around one peak period) rather than a blanket freeze across all services.

**Patterns found.**
- External/CAB approval negatively correlated with lead time, deployment frequency, and time-to-restore; no correlation found with change failure rate; organisations with this process reported 2.6x more likely to be low performers — DORA, "Streamlining change approval," https://dora.dev/capabilities/streamlining-change-approval/, and the 2019 Accelerate State of DevOps Report, https://dora.dev/research/2019/dora-report/2019-dora-accelerate-state-of-devops-report.pdf, industry research report (primary; the capability-page findings were fetched directly, but the 2.6x figure specifically is drawn from a search-engine snippet of the underlying report rather than a direct read of the PDF — say so).
- Recommended replacement: peer review captured in the delivery platform to meet segregation-of-duties, plus automated testing/CI gates for detection, with the CAB repositioned toward coordination and business-level trade-offs rather than per-change gatekeeping — same DORA source (directly fetched).
- ITIL 4 formally distinguishes pre-authorised "standard changes" (procedure fully documented, risk pre-assessed, prior outcomes predictable, no CAB required) from "normal changes" (broader or riskier, still routed through approval), and names a passing CI/CD pipeline as a valid "change authority" for standard changes — secondary summaries of ITIL 4 change-enablement practice (itsm.tools, "Change Enablement in ITIL 4," https://itsm.tools/change-enablement/; faddom, "ITIL Change Management Types," https://faddom.com/itil-change-management-types-standard-vs-normal-vs-emergency/), secondary sources describing the official (paywalled) Axelos/PeopleCert framework — the primary ITIL 4 text was not directly accessed, say so.
- Real-world variance among smaller/critical-adjacent teams: engineering-control substitutes for freezes (flags plus fast rollback/roll-forward) at a ~15-engineer order-fulfilment platform deploying multiple times daily year-round; selective, platform-scoped freezes (native mobile only) at a ~50-person food-delivery startup; short bounded freezes (two weeks, with pre-freeze cleanup work) at a ~25-person social app; release-train scheduling instead of freezes at JetBrains — Pragmatic Engineer newsletter (Gergely Orosz), "Code Freezes: Part 3," https://newsletter.pragmaticengineer.com/p/code-freezes-part-3, practitioner report based on named-company interviews (secondary/practitioner report, not peer-reviewed or company-published).

**Evidence quality.** The core causal claim (formal approval doesn't buy stability) is DORA's own measured, multi-year survey research — the strongest evidence tier available for this question, and the capability page itself was read directly. The specific 2.6x figure was verified only via a search snippet, not a direct read of the 2019 report PDF, and carries that caveat. The ITIL reconciliation claim rests on secondary summaries of a source that was not directly accessible. The company-variance examples are anecdotal and practitioner-reported (single-newsletter source, multiple named companies), and none of the interviewed companies are large-scale regulated or safety-critical systems in the sense the charter means by "critical services."

**Transfer to an agent.** Applies directly to S7 and reinforces the charter's D4 (no autonomous merge or deploy) and anti-goal against throughput optimisation. Rubric line: S6/S7 approval is a single named human decision per change, not a scheduling gate through a standing board; multi-party formal review is reserved for changes flagged high-tier at intake (RQ-S0-1), not applied uniformly to every change regardless of risk.

**Gaps.** Could not directly access the primary 2019 Accelerate State of DevOps Report PDF or the official ITIL 4 text (both effectively paywalled or unreadable by available tooling in this environment); both the 2.6x figure and the ITIL "change authority" claim are carried on secondary summaries and flagged accordingly. Searched for a specifically regulated or large-scale "critical systems" example (banking, healthcare) of this balance beyond a Team Topologies post titled "When DORA metrics meet governance in banking" that surfaced in search but was not fetched — this remains unexplored and is a genuine gap.
