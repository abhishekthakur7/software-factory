### RQ-S3-7. What heuristics do respected practitioners publish for when to introduce an abstraction, and has anyone operationalised them as a checklist or lint?

**Answer.** Practitioners converge on a small set of named heuristics rather than one unified rule: wait for the rule of three before extracting anything; treat accumulating parameters and conditionals inside a shared abstraction as the signature of a "wrong abstraction," and fix it by inlining back to duplication rather than adding more branches; prefer deep modules (simple interface, large hidden functionality) over shallow ones; and avoid hasty abstraction until the shape of future change is actually known (YAGNI/AHA). None of these has been operationalised as a lint that measures abstraction quality directly. The closest mechanical proxy is duplication-detection tooling (jscpd, SonarQube, PMD CPD), which flags repeated code past a line/token threshold — a proxy for "you've hit three occurrences," not for "this abstraction is wrong," which stays a judgment call about parameter and conditional growth.

**Patterns found.**
- Rule of three: don't abstract on the second occurrence, only when a third appears, because two instances can't distinguish real from coincidental similarity — [Rule of three (computer programming)](https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming)), Wikipedia, secondary/tertiary reference summarizing a widely-cited practitioner rule of thumb.
- "Wrong abstraction" signal is parameter/conditional accumulation in shared code; the fix is to inline the abstraction back into each caller, strip what each caller doesn't need, then re-extract once the real shape is understood; "duplication is far cheaper than the wrong abstraction" — [The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction), Sandi Metz, practitioner blog (primary, author is the source).
- Deep modules (simple interface hiding a lot of functionality) are preferable to shallow modules (complex interface, little hidden complexity); module depth is a cost (interface complexity) vs. benefit (functionality hidden) tradeoff — *A Philosophy of Software Design*, John Ousterhout, book (primary), summarized via [Deep vs shallow modules](https://www.sandordargo.com/blog/2023/01/25/deep-vs-shallow-modules) and [A Philosophy of Software Design summary](https://www.janmeppe.com/blog/a-philosophy-of-software-design-john-ousterhout/), practitioner blogs (secondary, book not fetched directly).
- AHA (Avoid Hasty Abstractions): optimize for change first; tolerate duplication until the abstraction is well-informed by real usage; sunk-cost pressure is named as the reason engineers cling to bad abstractions — [Avoid Hasty Abstractions (AHA)](https://www.epicweb.dev/principles/craft/architecting-projects/aha), Kent C. Dodds, practitioner site (primary).
- YAGNI applies to speculative capability, not to effort spent making code easier to change later — [Yagni](https://martinfowler.com/bliki/Yagni.html), Martin Fowler, practitioner blog (primary).
- Duplication detectors as the only mechanical proxy in wide use: jscpd flags blocks ≥5 lines by default; SonarQube requires ≥10 duplicated statements to flag a fragment and can gate a PR on a duplication-percentage threshold — [jscpd](https://github.com/MaelWeb/jscpd), [SonarQube duplication threshold discussion](https://community.sonarsource.com/t/duplicate-code-threshold/46854), tool documentation/community (primary for tool behavior).

**Evidence quality.** Primary for the individual heuristics (Metz, Fowler, Dodds are the originating practitioners writing on their own sites/blogs; Ousterhout is the originating book, reached via secondary summaries). All anecdotal/qualitative — no measured study found linking rule-of-three adherence, or duplication-lint pass rate, to defect rate or maintenance cost. Four independent practitioner sources agree on the "wait, don't guess" posture; none is company-internal data.

**Transfer to an agent.** Partially checkable. Rule of three is checkable as a rubric line: an agent proposing a new shared abstraction must cite at least three existing near-duplicate occurrences it is replacing, or justify why a first occurrence is being pre-abstracted (and that justification becomes a named risk). The "wrong abstraction" smell is partially checkable: flag when a plan or diff adds a new parameter and a new conditional branch to an existing shared function/class that already serves two or more unrelated call sites, and require the plan to say why inlining wasn't chosen instead. Module depth is not mechanically checkable; it should be a plan-review question ("does this module's public interface stay simple relative to what it hides?") rather than a lint.

**Gaps.** Searched for "abstraction linter," "shallow module detector," and "wrong abstraction lint" — found none. No company-published lint or CI gate that scores abstraction quality (as opposed to raw duplication) was located.

### RQ-S3-8. How do teams decide whether legacy or hacky code is load-bearing before changing it, and what written policy exists?

**Answer.** No single formalized, company-wide "load-bearing" decision procedure was found; the pattern is a bundle of informal norms rather than one written policy. The dominant framing is Chesterton's Fence — understand why code exists (via `git blame`, commit history, linked tickets, or asking a current/former owner) before removing or "fixing" it — invoked repeatedly across practitioner and company blogs but not codified as a required workflow step anywhere found. The concrete technique for making that judgment testable is Feathers' characterization test: pin down current behavior with a test before touching untested code, so a change to that behavior becomes visible (test fails) rather than silent. Written "do-not-touch" annotations exist only as ad hoc code comments, not as a standardized company mechanism.

**Patterns found.**
- Chesterton's Fence applied to code: check `git blame`, commit messages, and consult team members before changing code whose purpose is unclear — [Understanding Chesterton's Fence](https://medium.com/@mesw1/understanding-chestertons-fence-a-guiding-principle-in-software-engineering-7459e1fb7bf1), [Consider Chesterton's Fence Principle Before Changing That Code](https://josephwoodward.co.uk/2020/04/software-the-chestertons-fence-principle), practitioner blogs, secondary/anecdotal.
- Company framing of the same principle, with a named "when in doubt, don't touch it" default: "False Fences Make Bad Neighbors," Gusto Engineering — [engineering.gusto.com/false-fences-make-bad-neighbors](https://engineering.gusto.com/false-fences-make-bad-neighbors-26b007ced507), company engineering blog (primary), **fetch blocked (HTTP 403); used the indexed search snippet only, not the full text**.
- Characterization tests: write a test that documents current behavior, including its quirks, before modifying legacy code, so the test — not intuition — decides what "unchanged behavior" means — *Working Effectively with Legacy Code*, Michael Feathers, book (primary), summarized via [Key points of Working Effectively with Legacy Code](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/), practitioner blog (secondary).
- Direct application to agents: characterization is "the rare task where the agent does the bulk of the work and the human does the judgment" — the agent mechanically generates behavior captures, but a human must "promote" each capture as contract, accident, or irrelevant; the post explicitly argues an agent must not self-approve that a captured behavior is safe to drop — [Characterization Tests Are How Agents Enter Legacy Code](https://www.tddbuddy.com/blog/characterization-tests-are-the-on-ramp/), practitioner blog (primary), directly agent-focused.
- Informal "do not touch" code comments exist in the wild (e.g. cryptic warnings left by a prior engineer) but were not found codified as a company standard; the closest to a written rule found was an informal AI-refactor guideline stating auth/crypto/payment code and "unused" code require explicit owner review before touching — [Best Practices for AI Refactoring Legacy Code](https://www.codegeeks.solutions/blog/best-practices-for-ai-refactoring-legacy-code), practitioner/vendor blog, weak secondary evidence (vendor-content, treat with caution).

**Evidence quality.** Mostly secondary and practitioner-anecdotal; the strongest primary sources are Feathers' book (established practitioner canon, no measured figures) and the agent-specific TDD Buddy post (single practitioner source, not independently corroborated). No measured data found on how often "looked wrong but was load-bearing" judgments are made correctly or incorrectly. One source (Gusto) could not be fully verified due to a fetch block.

**Transfer to an agent.** This is the strongest and most directly agent-relevant hit in the packet, and it maps onto charter P5 ("not touching is the default... code that looks wrong is presumed load-bearing until its history says otherwise") and FM-02. Rubric line: before modifying or removing code whose purpose is not self-evident from the diff, the agent must retrieve git blame/history and any linked ticket for the touched lines, generate a characterization test capturing current behavior if none exists, and if the intended change would alter captured behavior, name that as an explicit risk in the plan rather than proceeding silently — the agent proposes, a human decides whether the captured behavior is load-bearing or accidental.

**Gaps.** No published quantitative data found on misclassification rates for "load-bearing" judgments. No named, company-wide formal "do-not-touch" annotation standard found (only informal, ad hoc examples). Gusto's primary post could not be fetched in full (403); its content here rests on the search-index snippet only.

### RQ-S3-9. How do organisations keep refactoring separate from feature changes, and when do they require a refactor to be split into its own change?

**Answer.** This is the most convergent and mechanically stated heuristic in the packet. Google's written code-review practice states directly that pure refactors and functional/behavioral changes belong in separate changes, because reviewing a mechanical refactor and reviewing a conceptual feature are different tasks and mixing them hides bugs in the noise; small local cleanups may ride along, but refactor-only changes must carry tests (added if missing) proving behavior is unchanged. Fowler frames the same discipline from the authoring side: work in one of two "hats" at a time — refactoring (behavior-preserving, tests stay green) or feature-addition (open-ended, tests may go red) — and do the preparatory refactor first, as its own step, so "you make the change easy, then make the easy change" (Kent Beck). At organizational scale, Uber runs large migrations (JUnit 4→5, Thrift→gRPC, Go context propagation) as dedicated, automated, separately-tracked efforts entirely decoupled from any feature work.

**Patterns found.**
- "It's usually best to do refactorings in a separate CL from feature changes or bug fixes... moving and renaming a class should be in a different CL from fixing a bug in that class." Small cleanups (e.g. a local variable rename) may be bundled into a feature CL; pure-refactor CLs "should also be covered by tests; ideally these tests already exist, but if they don't, you should add them" — [Small CLs, Google eng-practices](https://google.github.io/eng-practices/review/developer/small-cls.html), company practice doc (primary).
- "Two hats" — refactoring mode (behavior-preserving, small safe steps) vs. feature-addition mode (open-ended, riskier); preparatory refactoring means restructuring the code to make the coming feature easy to add, done as its own step first — "make the change easy, then make the easy change" (Kent Beck, quoted by Fowler) — [An example of preparatory refactoring](https://martinfowler.com/articles/preparatory-refactoring-example.html), Martin Fowler, practitioner blog (primary). The article does not state explicitly whether the preparatory step must be a separate commit/PR — it frames the separation as a mode of working, not a repo mechanic.
- Uber ran the JUnit 4→5 migration (>600,000 tests across ~15M lines of code) as its own automated effort, migrating >75,000 test classes and >1.25M lines of code over 4 months via >5,000 generated diffs, independent of feature work — [How Uber Executed A JUnit Migration at Massive Scale](https://www.uber.com/en/blog/junit-migration/), company engineering blog (primary).
- Uber's combined large-scale migrations (Experimentation API upgrade, annotation-processor modernization, feature-flag cleanup) generated 4,881 pull requests in six months (~800/month) as dedicated migration tooling output, separate from feature PRs — summarized in [Uber: LLM-Driven Developer Experience and Code Migrations at Scale](https://www.zenml.io/llmops-database/llm-driven-developer-experience-and-code-migrations-at-scale), secondary summary of primary Uber material.

**Evidence quality.** Primary company practice doc (Google, explicit written policy) plus primary practitioner authority (Fowler, on authoring discipline) plus primary company blog with measured figures (Uber, on migration scale). Three independent sources agree on the same norm — separate refactor from behavior change — though the Uber figures speak to scale and automation of migrations rather than to a controlled comparison of bundled-vs-separate review outcomes.

**Transfer to an agent.** Strong transfer; arguably the single most rubric-ready heuristic in this packet. Rubric line: if a proposed diff's entire justification is "no observable behavior change," it must be planned and landed as its own change, before or apart from any feature change touching the same code, and must carry tests demonstrating behavior is unchanged; a plan that bundles a refactor with a feature change must explicitly name and justify the exception (e.g. "trivial rename, <5 lines"). This maps to FM-04 (tech debt silently mixed into feature diffs) and P3 (front-load planning effort).

**Gaps.** No measured study found directly comparing review time or defect rate for bundled vs. separated refactor+feature diffs specifically (the general change-size-vs-review-time literature is closer to RQ-S3-3's territory — see cross-references). No explicit Fowler statement on commit/PR-level separation, only mode-of-working separation.

### RQ-S3-10. How do organisations enforce "use existing patterns and utilities" beyond linters, and what is transferable to a rubric?

**Answer.** Three non-lint mechanisms recur: human certification/mentorship programs that gate who may sign off on style (Google's readability process); platform-provided "golden path"/"paved road" catalogs that make the approved existing pattern the path of least resistance rather than something an engineer has to already know about (Spotify Golden Path, Netflix Paved Road); and searchable internal software catalogs that make existing services, libraries, and utilities discoverable so engineers don't reinvent them out of ignorance (Backstage). None of these is itself a checkable rule in the lint sense — they are organizational infrastructure that makes the existing pattern easy to find and, in Google's case, gates review authority on demonstrated internalization of it.

**Patterns found.**
- Google's readability process: a centralized group of certified reviewers reviews an engineer's CLs against language-specific best practice and style; comments decrease as the author internalizes the guidance, and the engineer eventually "graduates" and gains authority to review others on style; until certified, CLs need sign-off from someone who has it — *Software Engineering at Google*, Ch. 3 and Ch. 9, [abseil.io/resources/swe-book](https://abseil.io/resources/swe-book/html/ch09.html), company book (primary); further detail in [Readability: Google's Temple to Engineering Excellence](https://www.moderndescartes.com/essays/readability/), ex-Googler practitioner blog (secondary).
- Spotify's Golden Path has three components — path definition (what gets paved), a tutorial layer, and auto-scaffolding so new services start on the paved path by default, explicitly to counter "rumor-driven development" where engineers reinvent things because they don't know the sanctioned pattern exists — [How We Use Golden Paths to Solve Fragmentation in Our Software Ecosystem](https://engineering.atspotify.com/2020/08/how-we-use-golden-paths-to-solve-fragmentation-in-our-software-ecosystem), Spotify Engineering, company blog (primary).
- Netflix's Paved Road: a centralized platform team pre-assembles standardized, supported components and tooling so following the sanctioned pattern is easier than going off it, while still allowing (visible, deliberate) deviation — summarized in [The "Paved Road" PaaS for Microservices at Netflix](https://www.infoq.com/news/2017/06/paved-paas-netflix/) and [The Power of Paved Roads](https://seifrajhi.github.io/blog/paved-roads-netflix-developers/), secondary summaries of Netflix talks (Dianne Marsh, Yunong Xiao); no primary Netflix engineering-blog post was located.
- Backstage's software catalog gives a single searchable interface for services, APIs, and libraries across an org specifically to reduce duplicate-because-undiscoverable utilities, with automated ingestion (e.g. scanning repos on a schedule for a catalog descriptor file) rather than manual registration — [Backstage Software Catalog](https://backstage.io/docs/features/software-catalog/), official tool documentation (primary).

**Evidence quality.** Primary company sources for Google and Spotify; Netflix reached only via secondary talk summaries (no primary blog post found); Backstage is official but generic tool documentation, not a measured outcome study. No source in this set reports measured adoption rates, duplication-reduction figures, or defect impact for any of the three mechanisms.

**Transfer to an agent.** Partial. The certification/mentorship model has no direct agent analogue (there is no agent equivalent of "earning readability"). The catalog-discoverability idea does transfer: an agent should be required to check a named internal index of existing components/utilities before introducing a new one, and to record in the plan why an existing match was rejected if one was found. Rubric line: before proposing a new utility, pattern, or abstraction, the agent queries the internal component/service catalog (or equivalent repo-local index) for an existing equivalent and names, in the plan, why any existing candidate was rejected — checkable as "is this section present and does it name a search performed," not as "was the judgment correct."

**Gaps.** No measured evidence found on golden-path/paved-road adoption rates or their effect on duplication or defect rates. No primary Netflix engineering blog post located (talk-derived only). No lint or CI tool found that mechanically verifies "an existing utility was checked before adding a new one" beyond basic import-existence checks.

### RQ-S3-11. How do teams identify the highest-risk parts of a change in advance, so review attention can be pointed at them?

**Answer.** Two independent, measured methods converge, plus a recent production system at Meta that operationalizes both at scale. Hotspot analysis (Tornhill) ranks files by churn × complexity, on the premise that complexity only matters where people actually have to keep working in it. Microsoft Research's code-churn work found that relative (size- and time-normalized) churn measures — not absolute churn — discriminated fault-prone from non-fault-prone Windows Server 2003 binaries with 89.0% accuracy. A companion Microsoft Research ownership study found that low top-owner concentration and a higher count of low-expertise ("minor") contributors correlate with pre- and post-release failures across Windows Vista/7, Eclipse, and Firefox, and that minor-contributor edges specifically carry most of the ownership-based predictive signal. Meta's Diff Risk Score (DRS), launched 2025, is a production system built on these same underlying signals (a fine-tuned LLM scoring each diff's likelihood of causing an incident) and is used to route review attention, reviewer assignment, and code-freeze exceptions.

**Patterns found.**
- Hotspot Score = churn (change frequency) × complexity (lines of code, or cyclomatic complexity in the CodeScene product); temporal coupling (files that change together) is tracked as a related signal — *Your Code as a Crime Scene*, Adam Tornhill, book (primary), method also documented at [codescene.com/blog/author/adam-tornhill](https://codescene.com/blog/author/adam-tornhill), practitioner/tool-vendor documentation (primary, author's own material).
- Relative code churn measures (churn normalized by component size and time) predicted defect density; the churn metric suite discriminated fault-prone from non-fault-prone binaries with **89.0% accuracy**, case study on Windows Server 2003; absolute churn alone was a poor predictor — Nagappan & Ball, "Use of Relative Code Churn Measures to Predict System Defect Density," ICSE 2005, [microsoft.com/en-us/research/publication/...](https://www.microsoft.com/en-us/research/publication/use-of-relative-code-churn-measures-to-predict-system-defect-density/), peer-reviewed paper (primary).
- Ownership measures — proportion held by the top owner, and count of "minor" (low-expertise) contributors — relate to both pre-release faults and post-release failures across Windows Vista, Windows 7, Eclipse, and Firefox; removing minor-contributor edges "dramatically decreases" the performance of contribution-based defect predictors, indicating minor contributors carry most of the predictive signal — Bird, Nagappan et al., "Don't Touch My Code! Examining the Effects of Ownership on Software Quality," ESEC/FSE 2011, [microsoft.com/.../bird2011dtm.pdf](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/bird2011dtm.pdf), peer-reviewed paper (primary).
- Meta's Diff Risk Score (DRS): a fine-tuned Llama model scores each diff's likelihood of causing a production incident (SEV) from the code change and its metadata; it powers roughly 19–20 risk-aware features (reviewer selection, build/test selection, release risk analysis, code-freeze exceptions); during a 2024 partner event it allowed 10,000+ changes that previously could not have landed during a freeze to land "with minimal production impact" — [Diff Risk Score: AI-driven risk-aware software development](https://engineering.fb.com/2025/08/06/developer-tools/diff-risk-score-drs-ai-risk-aware-software-development-meta/), Meta Engineering blog, company engineering blog (primary).
- Independent academic study of Meta's system reports DRS is optimized for high recall at a fixed flag rate, e.g. "flagging 10% of diffs while catching 60% of PI-causing changes," and underlies RADAR's risk-gated automated review — "Automating Low-Risk Code Review at Meta: RADAR, Risk Calibration, and Review Efficiency," [arxiv.org/abs/2605.30208](https://arxiv.org/abs/2605.30208), peer-reviewed/preprint paper (primary-ish, external study with Meta data).

**Evidence quality.** Two independent, peer-reviewed Microsoft Research papers with measured accuracy on real large systems (denominators: Windows Server 2003 binaries; Windows Vista/7, Eclipse, Firefox commit histories), plus one practitioner/tool-vendor method (Tornhill/CodeScene) that operationalizes churn×complexity commercially, plus a primary, recent (2025) company blog and an independent academic evaluation of a production system (Meta DRS) with a measured recall/flag-rate figure. Four largely independent sources agree that historical change frequency, complexity, and ownership concentration are measurable, not just intuitive, risk signals. No equivalent published methodology or figures were found for Google's internal risk tooling specifically.

**Transfer to an agent.** Strong — the most directly quantifiable and most production-validated heuristic in this packet, and the underlying data (git history, blame, commit frequency) is already available to a repo-connected agent. Rubric line: for each file touched by the plan, the agent computes change frequency over a fixed window and an ownership-concentration measure (share held by the top committer/reviewer), flags any file in the top decile of churn×complexity or with no clear owner as a named entry in the plan's risk map, and states which specific reviewer attention it warrants — directly satisfying the charter's S3 risk-map requirement and P9 ("reviewable reasoning over reviewable diffs").

**Gaps.** No public methodology or figures were found for a Google-specific internal change-risk model (searched directly; only Microsoft's published academic work and Meta's DRS were retrievable — Google's equivalent, if it exists, is not publicly documented). Meta's own blog post did not disclose accuracy/recall figures directly; those came from an independent academic paper studying the system, not from Meta's own publication.
