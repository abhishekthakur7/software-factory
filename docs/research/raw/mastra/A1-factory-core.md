## 1. What Mastra does here

### 1.1 Boards as typed, validated data — `defineBoard()`

`mastracode/factory/src/boards/define-board.ts`. A board is a frozen object built by `defineBoard({ id, title, initialPhase, phases, tools?, transitionPolicy? })`. Construction-time validation (`BoardDefinitionError`) enforces: board and phase ids are 1–128 lowercase-insensitive identifiers (`IDENTIFIER_RE = /^[a-z0-9][a-z0-9_-]*$/i`); every phase declares a `kind`; a `working` phase must declare a `role` matching the same identifier rule, and only a working phase may; `initialPhase` must itself be `kind: 'resting'`; a phase's `next` and `outcomes` are mutually exclusive, and every named target must exist; tool-rule leaves may contain only `onResult`. The function derives frozen lookup tables at build time: `transitions` (`(from) -> [{outcome, to}]`), `rules` (`(phase) -> (source) -> {onEnter?, onExit?}`), and helper closures `allowsTransition`, `phaseKind`, `isWorking`, `isTerminal`, `roleForPhase`, `phaseForRole`. Everything returned is `Object.freeze`d, so a board is immutable data once defined, not a class instance with mutable state.

Two boards ship built in: `work` (`mastracode/factory/src/boards/work.ts`, phases `intake → triage → planning → execute → review → done|canceled`, roles `triage/plan/work/work`) and `review` (`review.ts`, phases `intake → review → done|canceled`, role `review`). `mastracode/factory/src/boards/registry.ts` reserves the ids `work` and `review`; `createBoardRegistry({ boards, includeDefaultBoards })` refuses a caller board that reuses a reserved id or a duplicate id among the caller's own boards. A deployment can add arbitrary custom boards (a worked "release" board rehearsal is in the README) or drop the defaults entirely (`includeDefaultBoards: false`).

### 1.2 Phase semantics — the `kind` taxonomy

`mastracode/factory/src/boards/semantics.ts`. Every phase is exactly one of three kinds, and the kind — not the phase's name — drives every consumer:

- **`resting`** — nobody seated; a human's move *out* of it arms autonomy, a move *back into* it disarms; `initialPhase` must be resting (a card cannot arrive already seated or already finished).
- **`working`** — an agent seat (`role`) carries the card; the seat is where a human kickoff opens and where a rule-started run leaves rest for.
- **`terminal`** — the card is finished; entering it releases the sandbox, lets sweeps supersede stale decisions, and revokes run bindings.

`resolvePhaseSemantics(boards, boardId, phase)` returns `undefined` when the board isn't installed or the phase isn't declared, and every caller (consent arming, the external-author guard, kickoff seating, run-start lane selection, terminal cleanup, closed-PR/issue sweeps, supervisor findings) is written to fail closed on that `undefined` rather than guess from the phase's string name. A custom board that reuses `work`'s phase names (`intake`, `planning`, ...) inherits nothing — kind and role are per-board declarations, never inferred.

### 1.3 Board transition policy — the third, separate concern

`mastracode/factory/src/boards/transition-policy.ts`, wired into `mastracode/factory/src/boards/work-transition-policy.ts` (`workTransitionPolicy`). Boards separate three concerns: **topology** (`phases`/`transitions`, which moves exist at all), **policy** (`transitionPolicy`, which of those moves is *allowed* given who is asking and what the item currently holds), and **lifecycle handlers** (`onEnter`/`onExit`, what effects follow). A policy function receives a deep-frozen, JSON-only snapshot (`immutablePolicySnapshot`, which throws on any non-plain-data value including functions/symbols, and turns `Date` into an ISO string rather than freezing a mutable `Date`) of the item, actor, ingress, source, `fromStage`/`toStage`, `itemRevision`, `isHumanTransition`, and persisted vs. requested classification. It returns `undefined` (no extra restriction), `{type:'allow', triageType?, accept?}`, or `{type:'reject', code, reason}` — a fixed `z.discriminatedUnion` schema (`boardTransitionPolicyResultSchema`) validates the shape and the rejection `code` against an enum. Work's own policy (`work-transition-policy.ts`) does two things with this: it requires a `triage`-role agent to report a structured `triageType`, and it blocks a non-bug classification from entering `planning`/`execute` without either `isHumanTransition` or a prior `acceptedAt` stamp — "passing through Review does not grant approval" (README). `isHumanTransition` is strict: it requires **both** `actor.type === 'human'` **and** `ingress.type === 'human'`, so a rule replaying a decision that merely *carries* a human's id (e.g. `approvedBy`) is not treated as a live human decision. Policies are documented as side-effect-free, run on initial entry/reentry/same-stage requests, and cannot themselves apply a patch — the runtime validates and applies the `triageType`/`accept` intent only inside the revision-checked commit, after every lifecycle handler has also allowed the move.

### 1.4 Lifecycle rules and tool-result rules

Declared inline on each phase (`onEnter`/`onExit`, keyed by source `issue|pullRequest|linearIssue|manual`) and, separately, at board level under `tools: { <toolName>: { onResult } }` (`mastracode/factory/src/boards/work-tool-rules.ts`, one rule: `advanceApprovedPlan`, which watches for a `plan`-role agent's `submit_plan` result starting with `Plan approved.` on a `planning`-stage card and returns a `transition` decision to `execute`). Resolution (`mastracode/factory/src/rules/resolve.ts`) is fail-closed by construction: a tool result on a card whose board isn't installed, or whose board doesn't declare a rule for that exact tool name, fires nothing — no inheritance across boards even when phase/role names collide.

Handlers return one typed **decision** or `undefined` (never an array; a rule that wants several effects returns them from separate onEnter/onExit/tool leaves, or the transition service accumulates one `exit` + one `enter` decision per move). The decision union (`mastracode/factory/src/rules/types.ts`) is: `reject`, `transition` (board/stage/optional message/optional `reenter`), `upsertLinkedWorkItem` (create-or-route a linked card onto another installed board), `invokeSkill` (start a run: `skillName` xor `prompt`, plus `role`, `idempotencyKey`, optional `cancelInFlight`), `sendMessage` (wake or persist a message to the item's active session), `notify` (a UI badge). Every decision carries an `idempotencyKey`; `mastracode/factory/src/rules/validation.ts` enforces bounded field lengths, exact-key objects (no stray fields), an identifier pattern for board/stage/role/tool names, JSON-metadata sanitisation that **redacts any key matching `/authorization|cookie|credential|password|secret|token/i`** recursively, and de-duplicates idempotency keys within one batch.

### 1.5 The transition service — the one place state actually moves

`mastracode/factory/src/rules/transition-service.ts` (`FactoryTransitionService.transition()`). Per request it, in order: (a) replays by `ingress.identity` if this exact ingress already committed (idempotent retry); (b) loads the item and resolves its board (persisted `board`, or the legacy default — `review` for a pull request, `work` otherwise, for pre-board rows); (c) rejects if the requested board doesn't match the item's actual board, or the board isn't installed; (d) rejects if the item's current single stage isn't declared on that board, or the board's topology doesn't allow `from -> to`; (e) evaluates `transitionPolicy` inside a 5s timeout race (`withRuleTimeout`); (f) applies the **external-author safety guard**: an agent actor moving a card from a non-working into a working phase on an item whose GitHub source is not a trusted, factory-authored write is rejected with `approval_required` regardless of what the policy said — "board allowance cannot bypass this guard"; (g) runs the resolved exit-then-enter lifecycle handlers, collecting decisions, validating each, and checking `assertFactoryDecisionTarget` (a `transition`/`upsertLinkedWorkItem` decision's board must be installed, its stage must exist on that board, and a `transition` may never change the item's own board); (h) if a human physically moved the card (`humanMove`), prepends/annotates a `sendMessage`/`invokeSkill.precedingMessage` telling the bound session "This work was moved from X to Y"; (i) commits everything — state, decisions, and the *consent* intent (`autonomy: 'arm'|'disarm'`, tied to `bearsConsent(actor)` = human or agent, never a bare webhook/rule) — atomically in one storage call keyed by `expectedRevision`; (j) if the destination is a `terminal` phase on the *installed* board, awaits `onTerminalStage` (sandbox release) up to a 30s bound, continuing in the background past it, never rolling back the already-committed transition. Rejection reasons are truncated to 512 bytes; a thrown rule or a 5s timeout is turned into `rule_error`/`timeout`, never left unhandled. `MAX_FACTORY_RULE_CAUSAL_DEPTH = 8` bounds how deep a chain of rule-triggered decisions triggering further decisions can nest, so a misconfigured custom board cannot cascade forever.

### 1.6 Storage domains and record shapes

`mastracode/factory/src/storage/domains/`. Each is a narrow, single-purpose table group behind its own interface (`*Storage`):

- **`work-items`** (`work-items/base.ts`) is the card itself: `WorkItemRow` — `id, orgId, factoryProjectId, board, externalSource, parentWorkItemId, title, stages[], stageHistory[], sessions, metadata, triageType, autonomyArmedAt, plansPreapprovedAt, acceptedAt, commentCount, feedActivityAt, revision, createdBy, createdAt, updatedAt`. `stageHistory` entries carry `stage, enteredAt, exitedAt?, by, exitedBy?` (actor attribution on both ends of a visit). Same file also holds `FactoryDeferredDecisionRecord` (a parked decision awaiting dispatch: `status` one of `pending|proposed|dismissed|superseded|leased|retry|succeeded|failed`, `attempts`, `deliveryGeneration`, `failureOccurrence`, `availableAt`, `leaseOwner`/`leaseExpiresAt`, `lastError`, `failureCode`, `approvedAt`/`approvedBy`), `FactoryRunBindingRecord` (the seat: `workItemId, role, threadId, resourceId, sessionId, branch, status: active|revoked`), `FactoryPendingStartRecord` (kickoff delivery), `FactorySupervisorFindingRecord`, `FactoryAttentionReceiptRecord` (per-user read/archive state over a small closed set of attention kinds), and `FactoryRuleEvaluationRecord` (one row per rule evaluation, replay key = `ingressId`).
- **`comments`** (`comments/`) — the work item's activity feed, with its own `schema.ts`, mention parsing, and a feed-context/feed-sync seam so the dispatcher can inject "recent comments" into a kickoff.
- **`audit`** (`audit/base.ts`, `domain.ts`, `agent-audit.ts`) — a generic append-only `AuditEventRow` keyed by `action`/`targets`/`metadata`, with a pluggable `AuditSink[]` fan-out, actor-profile caching (name/avatar stamped at record time so every auth provider works without a `getUser(id)` call), and a **detector** (`observeAgentGitAction`) that watches an agent's `execute_command` tool calls for `git commit`/`git push` (heredoc-body-stripped regexes) and emits `factory.agent.commit`/`factory.agent.push` audit rows — agent-caused git side effects are audited even though they never touch a web route.
- **`intake`**, **`integrations`**, **`credentials`**, **`custom-providers`**, **`model-packs`**, **`memory-settings`**, **`source-control`**, **`projects`**, **`filesystem`**, **`queue-health`**, **`channel-identity`** round out the domain list — each a thin table behind an interface, composed by `factory.ts`.

### 1.7 The deferred-decision dispatcher — autonomy, consent, retry

`mastracode/factory/src/rules/dispatcher.ts` (`FactoryDecisionDispatcher`, ~1200 lines; read in full). A poll loop (`POLL_MS = 1s`, `BATCH_SIZE = 10`, `MAX_IN_FLIGHT = 25`) leases pending decisions (`LEASE_MS = 30s`) and executes them. Key mechanisms:

- **Consent gating** (`#needsApproval`): a decision "needs approval" only if it `requestsConsent` (`invokeSkill` always does; a `transition` does only when the actor is external — i.e. not human/agent/system — *and* the destination phase's kind is `working`, defaulting to `working`/consent-required when the board/phase can't be resolved — fail closed) **and** `record.approvedAt === null`. Given consent is required, an externally-authored item (`externallyAuthoredWorkItem`) *always* needs approval — arming or auto-run is never standing consent for code from outside the write-access circle. Otherwise, an item with `autonomyArmedAt` set skips approval (a human already started this item; the runs that carry it onward are the same request continuing), and failing that, approval is needed unless the tenant's `isAutoRunEnabled` flag is on.
- **Proposal parking and supersession**: a decision that needs approval is written `proposed` rather than executed. `#supersedeProposals` marks a card's other pending/proposed decisions for the *same role* superseded once one of them actually starts running — "a proposal is a question... once that run is starting anyway... the card must stop asking it" (comment) — so a stale "should this run?" badge never outlives the run it asked about. `#supersedeFailureOnSettledCard` does the mirror-image cleanup: a decision that fails *after* its card already reached a terminal phase is silently marked superseded rather than paging a human about work nobody can act on any more.
- **Retry/backoff**: `retryAt = now + min(1000 * 2^(attempts-1), 60_000)`, `MAX_ATTEMPTS = 5`, `isTerminalFailure` also consults a per-failure-code `canRetry` flag (`dispatch-errors.ts`) so a structurally unretryable failure (e.g. missing session) doesn't burn all 5 attempts before surfacing.
- **Run-watching** (`watchRun`): subscribes to the bound session's event stream, distinguishes `complete|aborted|error|suspended`, and — the one interesting wrinkle — auto-approves up to `MAX_PLAN_APPROVALS = 3` `submit_plan` tool suspensions when the tenant has `autoApprovePlans` on, so a fully hands-off run can re-plan after reading its own approval without a human in the loop, while a 4th suspension is left parked for a person. A run the registry stops showing without an observed end event fails **non-terminally** (so it's retried with a fresh kickoff) at a 10-minute heartbeat; a run still shown as active for `skillCompletionObservationTimeoutMs` (default 6h) fails as `run_overdue`, because "failing a run the registry still shows would kick off a duplicate into a busy session."
- **Error sanitisation**: `sanitizeDispatchError` regex-redacts `bearer|token|api[-_ ]?key|authorization` substrings and truncates to 512 bytes before any error text is persisted.
- **Staleness sweeps**: active run bindings older than `staleBindingTtlMs` (default 24h) are revoked on a slow (`10min`) cadence independent of the per-tick claim path, to bound legacy/leaked bindings without inflating every tick's work.

### 1.8 Terminal cleanup and the start coordinator

`mastracode/factory/src/rules/terminal-cleanup.ts` (`createTerminalStageCleanup`) runs, best-effort and in order, when a card enters a terminal phase: reconcile any trailing tool results on its active bindings, revoke those bindings, supersede decisions still parked on it, release its sandboxes — checking the item's *current* revision against the revision the terminal transition itself produced first, so a card re-entered for another pass after cleanup was scheduled isn't torn down underneath the new pass.

`mastracode/factory/src/rules/start-coordinator.ts` (`FactoryStartCoordinator.prepare`) is how a *human* kicks off work: resolves the source-control session, stamps `RequestContext` with `orgFirstCredentials: true` (org credentials win over the acting user's personal ones for a shared board run), sets `untrustedCheckout: true` (+ `baseRef`) on session state whenever the work item's source is a pull request — this is read by the coding-agent SDK to *skip loading `AGENTS.md`/`CLAUDE.md` from the checkout* into the system prompt, because those files are attacker-writable on a PR branch — hydrates the session with the factory's shared default model/memory settings (never an individual user's), sets the `factory_transition_work_item` tool's permission to `allow` (the tool itself is `requireApproval: true`; the coordinator's comment: "a person is reading the plan, not an approval queue... starting the run was already the say-so; the rules engine still governs"), and only then optionally drives one governed transition to the destination stage.

### 1.9 Agent-controller behaviour: the phase state processor and the transition tool

`mastracode/factory/src/rules/processor.ts` (`FactoryPhaseStateProcessor implements Processor<'factory-phase'>`) is the seam between the factory's record and the live agent context, via `@mastra/core/processors`' `computeStateSignal`/`processInputStep` hooks:

- `computeStateSignal` looks up the session's active run binding, re-reads the bound item and stage, and emits a **state signal** (`snapshot` on first render, `delta` afterward, deduped by a SHA-256 `cacheKey` over the phase value + up to 5 linked items) that becomes literal system-prompt text: `Factory {board} phase: {label} ({stage})\nWork item: {title} ({id})\nRole: {role}\nRevision: {revision}\nConfig: {configVersion}\n...\nUse factory_transition_work_item with expectedRevision {revision} to request a phase change.` — the agent is told its own governance coordinates on every turn, not asked to remember them.
- `processInputStep`/`ingestMessages`/`ingestToolResult` scan the transcript for completed tool calls, resolve `resolveBoardToolRule(board, toolName)`, and — if one fires — commit the rule evaluation (replay-guarded by `[bindingId, threadId, assistantMessageId, toolCallId]` as ingress identity) and immediately execute any resulting `transition` decision through the transition service. `reconcileAllBoundThreads`/`reconcileBinding` is the same ingestion run as a periodic sweep (paged `listMessages`, cursor-tracked) so a result missed at run end (a message ingested after the stream closed) is still caught.
- `mastracode/factory/src/rules/tools.ts` (`createFactoryTransitionTools`) is the actual `factory_transition_work_item` tool the agent calls: resolves the calling session's bound binding, re-derives the board from the item (never trusts a client-supplied board), only accepts `triageType` from a `triage`-role binding on the `work` board (a non-triage role can pass the key through — sessions are shared across role rotations — but it's silently ignored), and forwards to `transitionService.transition` with `actor: {type:'agent', bindingId, role}` and `ingress: {type:'agent', identity: `${bindingId}:${toolCallId}`}`. The input schema clamps an oversized `rationale` to 1000 chars with an ellipsis rather than rejecting it outright, "since providers strip maxLength from the JSON schema and models can't count characters" — accept-and-clamp instead of reject-and-retry-loop.

### 1.10 The supervisor — deterministic health check + a narrowly-scoped read agent

`mastracode/factory/src/supervisor/health.ts` computes `FactoryHealthReport` purely from storage rows, no model involved, so "the supervisor agent explains findings rather than inventing them, and the same list can be rendered by the UI or polled by a timer." Six finding kinds, each with a named standard repair: `decision-stuck` (retry/pending past its backoff, or an expired lease — the dispatcher isn't picking it up), `start-stalled` (a kickoff was asked for but never landed), `seat-orphaned` (a seat active on a card that already finished or left that role's lane — a lifecycle bug), `seat-missing` (a working-lane card with nobody bound and nothing in flight), `held-waiting` (a maintainer is the blocker), `label-drift` (GitHub labels disagree with the card's accepted state). Age thresholds are named config (`DEFAULT_HEALTH_THRESHOLDS`), not scattered literals.

`mastracode/factory/src/supervisor/instructions.ts` is the system prompt for a chat agent layered on top: it has **no repository and no sandbox**, only `factory_*` read tools (`factory_health_check`, `factory_list_attention`, `factory_inspect_work_item`, `factory_read_session`) plus confirmation-gated write/repair tools (`supervisor/write-tools.ts`), and is explicitly told: "Ground every claim in a tool result... Never guess at a cause the records do not show," "Never claim a repair happened unless a tool result says it did."

### 1.11 `factory-skills/` — what the factory ships its own agents

Six skills, each a `SKILL.md`: `factory-triage` (investigate, diagnose, request transition), `factory-plan` (produce a phased plan, transition to execute), `factory-review`/`factory-rereview` (review a PR, publish a verdict, transition), `factory-complete-issue` (close out GitHub labels/comment), `configure-factory-rules` (a meta-skill teaching an operator's agent how to edit `defineBoard()` calls safely — "Factory rules are trusted server code. Never place deployment policy in this skill, repository instructions, browser code, or a parallel actions system"). Every autonomous-pass skill repeats the same two disciplines verbatim: (1) "make `factory_transition_work_item` your terminal step... never wait for or solicit human input mid-run; every judgment call is yours to resolve" and (2) an assumption/question split — "record the decision as an assumption for the terminal handoff... Assumptions are for *interpretive* calls only... **A confirmed finding may never be resolved by recording an assumption**: if you verified a defect, it stays a finding and weighs into the verdict; writing 'treated as non-blocking' next to it does not make it non-blocking."

### 1.12 Lifecycle: `prepare()` / `new Mastra()` / `finalize()`

`mastracode/factory/src/factory.ts` (`MastraFactory`, 1221 lines). `prepare()` resolves feature readiness and assembles routes/middleware/integration defaults, returning constructor args; the literal `new Mastra(prepare())` must stay in the host's entry file (the deployer's static-analysis Babel plugin requires it); `finalize()` — called *after* that construction — initializes the agent controller, calls `reconcileAllBoundThreads()` on the phase processor (catch-up ingestion), and starts the dispatcher (`this.#dispatcher.start()`). `shutdown()` stops the dispatcher. This two-phase (`prepare`/`finalize`) split exists purely to satisfy the host framework's static bundling requirement — it is not itself a governance mechanism.

### 1.13 Product direction (`CHANGELOG.md`, newest entries)

The newest ~300 lines show: (a) the board/rules model in this packet is itself a *recent* generalisation — a prior version had one global `rules.work`/`rules.review` config object, replaced by per-board `defineBoard()` ownership plus a `configVersion` label (no functional branching, pure audit provenance) specifically so no rule can be silently overridden from outside the typed deployment config; (b) "autonomous first-pass skills" (triage/plan/review running the instant a card enters the matching column) replaced older *interactive* skills that stopped to ask questions mid-run; (c) a `stageAutomation` metrics breakdown (per stage: how many passes were entered-and-exited by automation on first visit, and how those resolved) was added with an explicit definition of "automation" narrow enough to exclude the rule-dispatcher's own repo-sync stamps, because a looser definition would pin the reported automation ratio near 100%; (d) `updateIssue`/external-issue-state-sync as a side effect of a transition, gated so it currently changes nothing (no rule emits the new decision yet) — shipped ahead of the rule that will use it; (e) an `AbortSignal`-bounded critical section around a DB advisory lock, added after an unbounded outbound call inside the lock could pin a pooled connection for up to 5 minutes.

## 2. What we already have

| Mastra mechanism | Our equivalent | How ours differs |
|---|---|---|
| `defineBoard()` + registry, custom boards | `runner/state_table.py` (`STATES`, `TABLE`, `STAGE_STATE`, `CLOSE_REASON`) + `runner/transitions.py` (`apply`, sole writer of `ticket.state`) | Fixed, not extensible: one board (14 states, R-I-1/R-F-11), enforced by a module the fence (R-F-11) keeps "outside `factory/`, outside the manifest, and beyond the reach of any proposal." Mastra ships an extensibility surface (custom boards, per-deployment `tools`/policy) we deliberately do not — Initial is one ticket type, one pipeline (Names/Greenfield rule; D24, D27 per `02-3-ticket-states.md`). |
| Phase `kind` (`resting`/`working`/`terminal`) | Implicit in `STAGE_STATE`, `TERMINAL_STATES`, `_ABANDONABLE`/`_MIGRATABLE` constants in `state_table.py` | We encode the same three-way split but as separate frozensets/tuples rather than one named field per state; no single place answers "is `checks` resting, working, or terminal" by lookup (see idea 3 below). |
| `BoardTransitionPolicy` (reject/allow+intents) | `runner/gates.py` (`intake_gate`, `plan_review_gate`, `checks_gate`, `review_gate`) deriving one event or `None` from already-recorded rows (quorum, freshness, waivers) | Structurally close: both separate "is this move even legal" (topology) from "is it currently *allowed*" (policy/gate). Ours derives the *event itself* from durable state rather than validating a client-requested move, so a repeated `advance` call is naturally idempotent (a no-op until the derived condition changes) rather than needing an explicit replay-by-ingress-id path. |
| `onEnter`/`onExit` lifecycle handlers, `invokeSkill` decisions | `runner/stages/*.py` stage drivers, dispatched by the (unbuilt-here but referenced) state machine one at a time, each stage one fresh agent invocation (R-I-2) | Same shape (an event triggers an agent invocation with governed inputs), but ours has no generic "decision" object or rule-triggered cascade — a stage driver *is* the handler, not a rule returning a typed effect that something else later executes. |
| Board tool-result rules (`submit_plan` → transition) | `factory_transition_work_item`-equivalent: S4/S6 stage drivers call `checks_and_gates`/`transitions.apply` directly after the agent's hand-off/hand-back artefact is validated | We don't watch arbitrary tool calls inside a transcript for a magic string; the stage driver structurally requires a hand-off/hand-back artefact (R-S4-1, R-S4-2) with `R-I-12` structural completeness before any transition is even considered — closer to Mastra's `invokeSkill` (a skill contract) than to its transcript-scanning `onResult` rule. |
| `FactoryTransitionService.transition()` (single choke point, revision-checked, replay-guarded, timeout-bounded) | `transitions.apply()` (single writer of `ticket.state`) + `runner/gates.py` + `runner/binding.py`/`runner/freshness.py` (not fully read here, cited via HLD C4) | Ours binds a transition to a **canonical, content-addressed subject hash** (`evidence_tuple.content_hash`, R-T-10) rather than a plain integer `expectedRevision`; approval quorum is a first-class `approval_record` table with expiry, distinct-actor, and fork-detection rules (R-T-10, "a forked head blocks the gate") rather than a boolean `isHumanTransition` check. Stricter by design — see §5. |
| `WorkItemRow` (board, stages[], stageHistory[], autonomyArmedAt, revision, ...) | `ticket` table (`runner/schema.py`), `stage_run` (one row per attempt, not per visit), `queue_item`, `evidence_tuple`, `approval_record`, `reviewer_set`, `waiver`, `guard_decision`, `tag`, `incident_observation` (full field lists: `docs/prd/02-2-entities.md`) | Far more granular: Mastra's `stageHistory[]` array (enter/exit/by/exitedBy) is one JSON blob per card; our `stage_run` is a first-class ledger row per *execution attempt* (not just per visit) carrying runtime/model identity, tokens, cost provenance, sandbox/toolchain digests, and lease fields — the ledger-at-execution-grain design C5 in the charter calls for. Mastra has nothing resembling our `evidence_tuple`/`approval_record`/`waiver`/`guard_decision` canonical-hash-and-expiry machinery. |

## 3. Portable ideas

### 1. Deterministic factory health report ("what's stuck right now")
**What it is.** A pure-function report (no model call) over already-recorded rows that enumerates a fixed, named set of anomaly kinds — a stuck/expired-lease run, a stalled kickoff, an orphaned or missing seat, a maintainer-blocked item past an age threshold — each with age evidence and a named standard repair, on config'd thresholds (`FactoryHealthThresholds`), consumable by a human or a script.
**Why it matters.** Our own crash-recovery rule (`docs/prd/02-3-ticket-states.md`, "On restart, the runner expires only a run whose lease and process identity are both dead...") already *repairs* dead leases automatically, but nothing surfaces "is anything currently wrong" as one artefact for the engineer running the dry-run pilot to read before typing `factory advance`. This is P11 (the factory as collaborator: a human-readable artefact plus the reasoning) applied to the runner's own operational state, not just to ticket work.
**Rating.** `next milestone`. Not required for Milestone A/B's definition of done (one ticket at a time makes most of these conditions rare), but small and immediately useful once the runner has run more than a handful of tickets, and cheap to build against tables that already exist.
**Where it lands.** New PRD row in `docs/prd/06-observability.md` (R-O area), a sibling to R-O-1's lease contract; extends `runner/queue.py`/`runner/operations.py`'s existing `report`/`show` verbs rather than a new component; HLD: extends the `factory` command (C1) in `L2-control-plane.md`'s diagram 1a (`C1_ops`), no new component needed.
**Draft acceptance criteria.**
- A `factory doctor` (or `report --health`) invocation returns zero findings against a ticket set with every lease fresh, every run bound, and no queue item past its age threshold.
- A `stage_run` whose `lease_expires_at` is past and whose process is dead produces exactly one finding naming the run id and elapsed time, distinct from the restart-time automatic repair (the finding is diagnostic, not itself a repair).
- A `queue_item` open past the configured age threshold produces one finding per item, grouped by ticket.
- must-reject: a `stage_run` still inside its lease window, or a `queue_item` younger than its threshold, produces no finding (no false positives from freshly-started work).
- Verification: script test over seeded fixtures at each threshold boundary (fresh, one second before, one second after).
**Size.** S.
**Copy vs. re-derive.** Copy the *shape* (named finding kinds, each carrying evidence + a suggested repair, computed from stored rows alone, no model in the loop) and the discipline of separate "the record already shows this to the human elsewhere" exclusions (Mastra explicitly excludes failed-decision/proposal findings from health because the queue already carries them — same principle applies to our own `queue_item`/`red_check` overlap). Re-derive the finding-kind list itself: our failure taxonomy (`stage_run.outcome`/`failure_kind`, `docs/prd/02-2-entities.md`) is already richer than Mastra's, so our health report's kinds should be named from *our* enums, not copied verbatim.

### 2. Bounded secret-redaction regex applied uniformly to stored freeform text
**What it is.** `sanitizeDispatchError` (`mastracode/factory/src/rules/dispatch-errors.ts`, referenced from `dispatcher.ts`) strips `bearer|token|api[-_ ]?key|authorization` substrings and truncates to 512 bytes before *any* error text is persisted; `normalizeFactoryRuleJsonValue` (`rules/validation.ts`) separately redacts any JSON key matching `/authorization|cookie|credential|password|secret|token/i` recursively before a rule's metadata is stored.
**Why it matters.** R-I-14 already promises "the value is never written to the record" for the one known runtime-key credential, and `tool_call`'s field description in `docs/prd/02-2-entities.md` already says "Credentials are stripped before digesting" — but that is a digest-time guarantee on `tool_call.args_digest`/`result_digest`, not a blanket rule applied to every freeform text field the runner stores verbatim (`stage_run.reasoning_summary`, `tag.note`, `check_result.summary`, `queue_item.note`). An agent's own reasoning text, or a human's free-text note, can echo something that looks like a secret without ever going through the guard's content-class machinery (that machinery classifies *artefact* content, not every short string field). This is a cheap defense-in-depth layer, cites FM-24 ("no ticket text... or secret" is the digest's own rule under R-H-3) and P7.
**Rating.** `must-have for dry run`. It is small, general, and closes a real gap between "the one credential we issue is never written" (R-I-14) and "nothing that looks like a credential is ever written" — worth having before any real ticket's agent-written text enters the record.
**Where it lands.** `docs/prd/02-2-entities.md` (a general rule on the `stage_run`/`tag`/`queue_item`/`check_result` free-text fields, or a new short requirement row in the same area R-T-9 lives), the record-writing helper in `runner/record.py` (not read this packet, but the natural single choke point, analogous to `runner/schema.py`'s already-centralized `once`/`mutable` column contract).
**Draft acceptance criteria.**
- A reasoning summary, note, or free-text field containing a string matching the secret-shaped pattern is written with that substring replaced by a fixed redaction marker, never the literal value.
- The redaction runs before the value reaches the database write, not as a display-time filter (so a direct DB read never exposes the original).
- must-reject: a value containing no secret-shaped substring is written byte-for-byte unchanged (the filter must not corrupt ordinary text).
- Verification: script test with fixtures containing common credential shapes (a bearer token, an API-key-looking string, an `Authorization:` header fragment) and a fixture with none.
**Size.** S.
**Copy vs. re-derive.** Copy the regex-and-truncate mechanism directly (it is language-agnostic and small). Re-derive the exact pattern list against our own credential shapes (the R-I-14 runtime key's format, any Jira/GitHub token shapes our adapters might see) rather than assuming Mastra's list is exhaustive for ours.

### 3. Name the three-way phase-kind taxonomy explicitly in our own state table
**What it is.** Mastra's `BoardPhaseKind` (`resting`/`working`/`terminal`) is one required field per phase that every other component (consent arming, sweeps, supervisor findings, terminal cleanup) reads instead of pattern-matching phase names.
**Why it matters.** "New" — no PRD row currently requires this; it is an internal-clarity and regression-safety improvement, not a behaviour change. `runner/state_table.py` already encodes the same three-way split, but split across three separate constants (`STAGE_STATE` implies "working", `TERMINAL_STATES` names terminal, resting is "whatever remains" — `intake`, `plan_review`, `checks`(as a gate wait), `pr_opened`). A single explicit mapping makes "is `plan_review` a human-wait state" answerable by lookup instead of by re-deriving it from which gate function exists for it, and would catch a state added later without updating every consumer.
**Rating.** `later`. Pure internal refactor with no externally visible behaviour change; not worth touching mid-pilot, but cheap to fold into a future `state_table.py` revision alongside any other change to that file.
**Where it lands.** `runner/state_table.py` only; no PRD row (documentation/code-shape only), no HLD change (C2's state machine already covers this at the concept level in `L2-control-plane.md`).
**Draft acceptance criteria.**
- Every state in `STATES` has exactly one declared kind among a fixed three-value set.
- A state whose kind is "working" corresponds to a state that has a driver in `STAGE_STATE` or is a human-wait gate state; a state whose kind is "terminal" is exactly `TERMINAL_STATES`.
- must-reject: adding a fourteenth state to `STATES` without adding its kind fails a schema/consistency test at import time, not silently.
- Verification: script test (already-present `state_table.py` invariants extended by one more).
**Size.** S.
**Copy vs. re-derive.** Copy the "one field, exhaustively checked at load" pattern; re-derive the three category names against our own vocabulary (we might prefer e.g. `waiting_on_human` / `agent_working` / `closed` to match how the PRD already talks about "human touchpoints").

### 4. Automation-attribution honesty check for first-attempt/automation measures
**What it is.** Mastra's CHANGELOG entry for `stageAutomation` explicitly narrows "automation" to exclude the rule-dispatcher's own mechanical repo-sync stamps ("counting those as machine work reports the repo's activity as the Factory's and pins any such ratio near 100%").
**Why it matters. ** R-O-5 and R-O-12 already forbid several specific vanity measures (agent-attributed PR share, estimated savings, per-person breakdowns) and require every context measure to be separately labelled — our discipline is already stricter than Mastra's here. This idea is not a new mechanism but a **caution to apply the same discipline** the next time a first-attempt or automation-share measure computation is written: make sure a mechanically-derived actor (our `factory-rule-dispatcher`/webhook-analogue, if one is ever added) is never folded into "agent did the work" the way Mastra's own comment warns against. Cites FM-22 (the measure-integrity failure mode R-O-5/R-O-12 both cite).
**Rating.** `next milestone`. Nothing to build now (R-O-10's observer pass and any automation-share measure are Later); this is a note to carry into that row's implementation, not a schema change today.
**Where it lands.** A one-sentence addition to `docs/prd/06-observability.md`'s "Share of stage runs passing on the first attempt" measure row, or wherever an eventual automation-share measure is defined; no HLD change; extends R-O-12's existing objective-rule row rather than a new one.
**Draft acceptance criteria.** (deferred until the measure exists; not drafted as a standalone row.)
**Size.** S (a documentation clarification, not code).
**Copy vs. re-derive.** Copy the caution itself, not any code — Mastra's `isAgentActor` function (`work-items/base.ts`) is TypeScript-specific plumbing with no direct analogue in our schema.

### 5. Sharpen S3/S6 skill or rubric text with the "a confirmed finding may never become an assumption" rule
**What it is.** The exact sentence from `factory-review`/`factory-rereview`/`factory-triage`: "record the decision as an assumption... Assumptions are for *interpretive* calls only... A confirmed finding may never be resolved by recording an assumption: if you verified a defect, it stays a finding... writing 'treated as non-blocking' next to it does not make it non-blocking."
**Why it matters.** We already have the schema half of this discipline (`assumption.origin`, `consequential`/`hard_to_reverse`/`blocking` booleans on `question`), but the packet's reading list didn't surface an equally explicit prose rule guarding against an agent *downgrading a confirmed problem into an assumption to avoid raising a question* — a specific, named failure mode (packets/questions must be self-contained and honest, R-H-8, FM-10) that a one-sentence rule closes cheaply wherever our own S3/S4/S6 skill or rubric text gives an agent this kind of judgment call.
**Rating.** `next milestone`. Text-only, costs nothing structurally, but belongs in the S3/S4/S6 skill files (which this packet did not read in full) rather than the PRD — flagging it here so it reaches whoever writes or reviews those skill files next.
**Where it lands.** `factory/skills/` (S3/S4/S6 agent-facing skill text, not read in this packet), possibly echoed in `docs/prd/07-factory-as-code.md`'s `rubrics/checklists/` (`comment-rules.md`-style file) if the owner wants it as a checked rubric line rather than prose alone. HLD: none (it's factory-as-code content, domain 5, out of this packet's scope).
**Draft acceptance criteria.** (skill-text change; not a schema-verified requirement row — would need R-S3/R-S4/R-S6's existing self-containedness rubric lines, not a new one.)
**Size.** S.
**Copy vs. re-derive.** Copy the sentence close to verbatim (it is already precisely worded); no code to re-derive.

### 6. Untrusted-checkout guard against attacker-controlled project-instruction files
**What it is.** `mastracode/factory/src/rules/start-coordinator.ts` sets `untrustedCheckout: true` (+ the trusted `baseRef`) on any session whose work item's source is a pull request, so the coding-agent SDK never loads `AGENTS.md`/`CLAUDE.md` from that checkout into the system prompt or reminders — those files are writable by whoever opened the PR.
**Why it matters.** This defends the exact class of attack our own `docs/design/hld/L2-record.md` diagram 1 already names at the artefact level (`R1_artefact`'s "untrusted-instruction mark on ticket/repo text, imported prose") — the general shape (content a stage agent will read that an outside party controls) is one we've already flagged as a governed-content concern (R-T-9/R-T-4). Cites FM-05 and FM-23 (trust boundary / execution boundary), the same failure modes R-I-3/R-I-11/R-I-14 cite for capability confinement.
**Applicability today.** Currently narrower than Mastra's exposure: our only agent-driven stage is S4 (implementation), which works inside a worktree on a ticket branch the *factory itself* created off an internal target base (R-S4-1's handoff, R-I-14's worktree mount) — not a PR authored by an unreviewed outside contributor. S5/S6 are scripts, not agents (`docs/prd/03-stage-interface.md`, "No agent runs on a ticket after S4"). Mastra's exposure comes specifically from its `review` board running a full coding agent over an externally-authored PR (`factory-review`/`factory-rereview`), which we have no equivalent of in Initial.
**Rating.** `later`. Not applicable to Initial's actual agent surface today (see above); becomes directly relevant the moment any Initial-scope agent stage is ever pointed at content whose branch/checkout a human hasn't yet reviewed — which is exactly the shape a Later S7/external-review expansion, or any future "agent reviews an external PR" feature, would have.
**Where it lands.** Not a PRD row today (no requirement is violated); flagged for whoever designs S7 or any future external-contribution path. HLD: would extend `R-I-14`'s sandbox/mount contract in a Later `L2-execution-boundary.md` entry.
**Draft acceptance criteria.** (not drafted; not in scope until the triggering feature exists.)
**Size.** — (not scoped).
**Copy vs. re-derive.** If/when relevant: copy the mechanism (a boolean session/sandbox flag suppressing project-instruction-file auto-loading from an unreviewed checkout, with an explicit trusted fallback ref) near-verbatim; it is a small, general, well-reasoned guard.

### 7. An explicit "hands-off once accepted" autonomy flag, separate from a global auto-run toggle
**What it is.** `WorkItemRow.autonomyArmedAt`: a human's first move of a card *out* of a resting phase arms it; the dispatcher then treats every subsequent run on that item as consented (skipping the "may the Factory pick this up on its own?" question) even while the tenant-wide auto-run toggle stays off, on the reasoning that "withholding auto-run decides what the Factory may pick up on its own, not whether it may finish work a person already handed it."
**Why it matters.** Every one of our human touchpoints today is a mandatory, individually-gated approval (R-H-4's full action list; `plan_review`'s full quorum; S5's `red_check`; S6's full review quorum) — there is no notion of "this specific ticket is pre-cleared to run further stages without a fresh per-boundary confirmation." That is a deliberate Initial choice (one ticket, one engineer, every gate matters at pilot scale), but Mastra's per-item arm/disarm flag is a clean, minimal shape for the *eventual* question of "once I've approved this ticket's plan, do I want every following stage to still stop and ask, or only the ones the PRD marks as a genuine decision point?" Cites FM-09 (the touchpoint/interruption failure mode most R-H rows already cite) and P1.
**Rating.** `later` — genuinely a question for the owner (see §4) before it becomes a requirement row at all; today's Initial scope has no toggle for it to attach to.
**Where it lands.** If adopted: `docs/prd/02-2-entities.md`'s `ticket` table (a new nullable timestamp column, directly analogous to `acceptedAt` which already exists there for the non-bug approval gate — this would generalise that single-purpose field into a broader "hands-off from here" flag), `docs/prd/05-human-interaction.md` (a new R-H row narrowing which *already-passed* gates a subsequent stage may skip re-asking, never which gates exist). New row, extends the `ticket` row of `docs/design/hld/L2-record.md`'s `R1_ticket`.
**Draft acceptance criteria.** (not drafted — depends on the owner's answer in §4; premature to specify clauses for a mechanism whose existence is still an open question.)
**Size.** M (touches the `ticket` schema, the queue's gating logic in `runner/queue.py`, and every R-H-4 action site that currently checks a gate unconditionally).
**Copy vs. re-derive.** If adopted: copy the *concept* (arm on a human's first working-phase move, never a blanket toggle) and the specific carve-out that an externally-authored item is *never* covered by arming (idea 6's guard and this one compose in Mastra — `#needsApproval` checks the external-author guard strictly before the arming shortcut). Re-derive entirely which of *our* gates, if any, the flag is allowed to skip — Mastra's "arming" only ever skips a *run-start* consent question, never a quorum/approval gate, and our R-H-4 gates are mostly quorum/approval, not run-start consent, so a naive port would weaken something Mastra never intended to weaken.

### 8. Centralize per-failure-kind retry policy as one lookup, the way `factoryDispatchFailureMetadata` does
**What it is.** `mastracode/factory/src/rules/dispatch-errors.ts` keys every dispatch failure code to one `canRetry` (and related) metadata record, so "is this failure kind retryable" is answered in exactly one place rather than re-derived at each call site.
**Why it matters.** Our own retry policy per `failure_kind` (`implementation`, `verification`, `infrastructure`, `sandbox_integrity`, `structural`, `expired_lease`, `stale_binding`) is currently expressed as prose spread across `docs/prd/02-3-ticket-states.md`'s "Failed and blocked runs" paragraph, `docs/prd/04-S4-implementation.md` (R-S4-5, R-S4-6), and presumably matching logic in `runner/operations.py`/`runner/stages/implementation.py` (not read in this packet). A single named lookup (even if it's only ever consulted by one caller today) makes a future audit of "which failures retry, how many times, and which escalate immediately" a one-file read instead of a cross-document search — the same value Mastra gets from centralizing it.
**Rating.** `next milestone`. Small, internal, no behaviour change if done as a pure refactor; worth doing once, not urgent for the dry run.
**Where it lands.** `runner/` only (a new small module, e.g. `runner/failure_policy.py`, consulted by `runner/gates.py` and the S4 driver); no PRD row (the *policy* is already fully specified by R-S4-5/R-S4-6/the 2.3 state table — this is a code-organisation port, not a requirement change); no HLD change.
**Draft acceptance criteria.** (refactor; verified by the existing failure-path tests continuing to pass, no new externally-visible behaviour to specify clauses for.)
**Size.** S.
**Copy vs. re-derive.** Copy the "one table, keyed by failure kind, consulted everywhere" shape; re-derive the actual retry counts/bounds, which our PRD already fixes precisely (three verification attempts, one infrastructure retry, zero retries for a structural/control-defect failure) and must not silently drift from Mastra's own numbers (`MAX_ATTEMPTS = 5`, exponential backoff capped at 60s) — those are Mastra's defaults for a generic decision queue, not ours for a fixed seven-stage pipeline.

## 4. Questions for the owner

Only questions whose answer changes what gets written into the PRD; plain words, a stated default for each.

1. **Should a ticket ever skip a human gate it has already effectively cleared once?** Right now every stage boundary that the PRD marks as a human touchpoint (plan approval, a failed check, the final review) always stops and waits, even on a ticket the engineer has already been actively steering for a while. Mastra lets a person's first move into working "arm" the item so later stages don't re-ask a run-start question, while still keeping every approval/quorum gate. Do we want anything like that for the pilot, or is "every gate, every time" exactly the point at this scale? **Default: no — keep every gate, since Initial is one ticket at a time and every touchpoint is small in absolute count.**
2. **Do we want a single "what's stuck" status view before the dry run, or is `factory show`/`report` already enough?** Idea 1 above (a deterministic health report) is cheap to build but is new surface area. **Default: build it — it costs little and directly serves the engineer running the pilot solo.**
3. **Should stored free-text fields (reasoning summaries, notes) get an automatic secret-redaction pass, or is the existing credential-never-enters-the-sandbox guarantee (R-I-14) considered sufficient on its own?** **Default: add the redaction pass (idea 2) — it is cheap and closes a real, if narrow, gap between "the one known credential is never written" and "nothing that looks like a credential is ever written."**

## 5. Do-not-port list

- **`defineBoard()` / multi-board extensibility, custom board registration, per-deployment GitHub/Linear webhook rule overrides.** Solves a problem we don't have: Mastra is a multi-tenant product serving many deployments with different pipelines; we are one factory, one ticket type, one fixed 14-state pipeline, and the PRD's own fence (R-F-11) exists specifically to keep that pipeline out of reach of *any* runtime configuration or proposal. Porting a board-definition framework would be building the exact flexibility our design intentionally forecloses.
- **incident.io integration, Linear intake, platform multi-tenant credential/telemetry plumbing (`MASTRA_DEPLOYMENT_ID`, `platform_hosted`, org-scoped PostHog events).** Out of scope by the owner's enterprise-tooling constraint (Atlassian + GitHub + Slack only, no other third-party integrations) and by hosting scale this pilot doesn't need.
- **`immutablePolicySnapshot`'s deep-freeze/defensive-copy machinery for policy callbacks.** Solves the problem of handing a mutable context object to *third-party-authored* policy code running inside the same process. We have no such extensibility surface (no operator-authored `transitionPolicy` functions) — every gate function in `runner/gates.py` is first-party runner code reviewed the same way the rest of the fence is; there is nothing external to defend against here.
- **`FactoryDecisionDispatcher`'s generic typed-decision queue (proposal/dismissed/superseded lifecycle, per-role decision supersession).** We don't have a generic "rule emits a decision, a dispatcher executes it later" architecture, and shouldn't build one just to match Mastra's shape — our stages already run synchronously one at a time (R-I-10's parallel limit of one), so there is no backlog of competing pending decisions to arbitrate. If a future milestone adds concurrency (R-I-10's capacity raise, gated by R-O-13 graduation), revisit; not before.
- **Terminal-stage sandbox-release coordinator (`createTerminalStageCleanup`).** Solves the problem of a sandbox held *across* an item's whole multi-stage lifetime. Ours is architecturally different: R-I-14 provisions and destroys a sandbox *per run*, not per ticket, so there is no persistent resource to release when a ticket reaches a terminal state — the problem this component exists to solve does not arise in our design.
- **`expectedRevision` as a plain integer for optimistic concurrency.** Weaker than what we already have. Our `evidence_tuple.content_hash` canonical-subject binding (R-T-10) is a cryptographic commitment over every field a decision actually depends on, not just a monotonic counter; adopting Mastra's simpler mechanism would be a regression, not a port.
- **`cancelInFlight` re-review supersession of a live agent run.** Solves the problem of a second run starting on a card that already has one live (Mastra's boards can, in principle, re-enter a working phase while a prior run on it is still active). Our stage drivers are structurally one-run-at-a-time per ticket (`stage_interface.py`'s `run_stage` binding "refuses a ticket with a live run" before ever reaching a driver), so there is no live run to cancel-and-restart in the first place.
