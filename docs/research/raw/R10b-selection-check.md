### RQ-T-8. Does Cursor publish an SDK, distinct from the CLI's non-interactive mode, and what does it expose per invocation?

**Answer.** Yes — as of this pass, Cursor publishes a documented SDK (`@cursor/sdk` for TypeScript, `cursor-sdk` for Python) that entered public beta on 2026-04-29, distinct from both the CLI's non-interactive mode and the separate Cloud Agents API/product. This directly corrects `R10-tooling.md`'s RQ-T-1 finding of "no SDK documented," which was based on a fetch of the CLI documentation index only (`cursor.com/docs/cli`) and evidently did not reach the separate `cursor.com/docs/sdk` and `cursor.com/docs/api` sections; the SDK's own announcement predates that R10 fetch by over four months, so the gap is a page-scope miss, not a genuinely new release. The SDK runs the agent loop in the engineer's own process when configured for the "local" runtime, but model inference itself is never local — "local does not mean the model runs locally: all inference goes through Cursor's hosted models in both modes," per the SDK's own documentation — and a separate "cloud" runtime configuration executes the whole agent in a Cursor-hosted VM instead. Per invocation, the documented TypeScript SDK returns token usage (input, output, cache read/write, optional reasoning tokens), a settled dollar cost, tool-call events with arguments and results, wall-clock duration in milliseconds, and the resolved model that actually executed; the model is selectable per call and hooks (`.cursor/hooks.json`) and rules files are documented as honoured in both runtime modes.

**Patterns found.**
- "The Cursor SDK is now in public beta... `npm install @cursor/sdk`... Programmatic agent creation with full capabilities (codebase indexing, MCP servers, skills, hooks, subagents)... Local runtime alternative for faster iteration... Cloud runtime option with dedicated VMs." Posted 2026-04-29 by Cursor staff in the Announcements category. — Cursor Community Forum, "Cursor SDK & Cloud Agents API updates," `https://forum.cursor.com/t/cursor-sdk-cloud-agents-api-updates/159284`, official announcement, fetched directly.
- "local does not mean the model runs locally — all inference goes through Cursor's hosted models in both modes." Runtime is selected by passing `local` or `cloud` configuration to `Agent.create()`. — Cursor Docs, "Cursor TypeScript SDK," `https://cursor.com/docs/sdk/typescript`, official documentation, fetched directly.
- Per-run return values: `TokenUsage` (input, output, cache read/write, optional reasoning tokens); a settled cost in dollars (absent initially, includes discounts); discriminated tool-call events for shell, edit, and MCP tool invocations with args and results; `durationMs`; a resolved `ModelSelection` naming the model that actually executed the request; final assistant text or error. — same source, fetched directly.
- Model selection is per invocation via the `model` parameter on `agent.send()`, and is sticky across subsequent sends unless overridden. Hooks are file-based at `.cursor/hooks.json` (project or user level); rules load from workspace configuration; MCP servers load from inline config, `.cursor/mcp.json`, `~/.cursor/mcp.json`, or the dashboard. — same source, fetched directly.
- "SDK runs follow the same pricing, request pools, and Privacy Mode rules as runs from the IDE and Cloud Agents." No explicit terms-of-use restriction on programmatic use was found on the SDK documentation page itself; billing routes through team or user plan API keys. — same source, fetched directly.
- The SDK is one of several distinct products under `cursor.com/docs/api`, alongside the separate Cloud Agents API (public Beta, cloud-only, Bearer/Basic auth), the Admin, Analytics, and AI Code Tracking APIs (Enterprise-only, cloud), and Bugbot and Origin APIs — the TypeScript and Python SDKs are the two listed as running with a local option. — Cursor Docs, "Cursor APIs Overview," `https://cursor.com/docs/api`, official documentation, fetched directly.
- Cloud Agents (the product, reachable without the SDK) run "exclusively in Cursor's cloud infrastructure, not on the engineer's local machine... they do not require your local machine to be connected to the internet," and are billed "at API pricing for the selected model." The Cloud Agents overview page does not itself document per-invocation token, cost, tool-call, or duration fields as standard output — that data model lives in the separate Cloud Agents API and SDK reference pages, not the product overview. — Cursor Docs, "Cloud Agents," `https://cursor.com/docs/cloud-agent`, official documentation, fetched directly.

**Evidence quality.** Primary throughout: the SDK's own reference documentation (fetched directly) for every per-invocation field, the API overview page (fetched directly) for the product taxonomy, and a dated, staff-authored forum announcement (fetched directly) establishing the SDK's public-beta launch date. One independent source (the forum post) corroborates the documentation's own framing that this is a beta-stage expansion of an existing agent, not a brand-new capability. No terms-of-use or licence document specific to programmatic SDK use was located beyond the pricing/Privacy-Mode line quoted above; this is a gap, not a contradiction.

**Fit to the inputs row.** Row 1 (the ledger, C5, D23) and the runtime choice cite D5 ("no bound expressed in runtime-specific units," "the choice for each stage is made from benchmark data") and D9 ("the pipeline runs on the engineer's machine first"). Against D9, the SDK's "local" runtime satisfies the letter of "runs on the engineer's machine" only for the agent-loop process and file access — the underlying model call always leaves the machine to Cursor's hosted inference, which is no different in kind from Claude Code CLI (also a hosted-model client) but is a materially different claim from "the CLI's non-interactive mode," since the SDK adds programmatic per-invocation token, cost, duration, and tool-call telemetry that the CLI's two documented output modes (per `R10-tooling.md` RQ-T-1) do not expose at all. Against C5 ("every invocation writes tokens, cost, wall-clock... tool calls"), the SDK is the first Cursor-side surface found in either packet that could actually populate `stage_run.tokens_in/out`, `stage_run.cost`, `stage_run.wall_clock_seconds`, and `tool_call.duration_ms` with runtime-reported (not price-table-estimated) values, which changes the calculus in `docs/prd/inputs.md` row 1's note ("no Cursor SDK is documented") — that note is now out of date and should be corrected, though whether Cursor's SDK reports cost as an authoritative billed figure or an estimate settled after the fact ("absent initially, includes discounts") still needs the same provenance-field treatment the PRD already gives Claude Code's cost fields. The note's other claim, that Cursor CLI reports durations only, is unaffected: the SDK is a distinct product from the CLI, confirmed by both being documented on separate pages with separate installation paths.

**Gaps.** No terms-of-service or acceptable-use document specific to SDK automation (as opposed to interactive IDE use) was located within budget; only the pricing/Privacy-Mode line on the SDK reference page addresses commercial terms. The exact cost-settlement mechanism (whether the dollar figure returned is Cursor's own billed amount or a client-computed estimate, and from what price table) was not documented on the fetched page beyond "absent initially, includes discounts" — this is the same open question the PRD already flags for Claude Code's cost fields and now applies to the Cursor SDK too. Python SDK's field-level parity with the TypeScript SDK (whether it exposes the same `TokenUsage`, `ModelSelection`, and tool-call event shapes) was not independently fetched and is inferred from the search snippet's description of "sync and async clients," not confirmed verbatim.

### RQ-T-9. Which projects called CodeGraph expose an MCP server for code navigation, and which of them could serve a Java service?

**Answer.** Two maintained projects named "CodeGraph" (case-insensitive) with an MCP server were identified and checked directly: `colbymchenry/codegraph` (MIT) and `codegraph-ai/CodeGraph` (Apache-2.0); both list Java explicitly among supported languages and both are the strongest candidates for a Java service. The 62%-fewer-tokens, 88%-fewer-tool-calls figure cited in `R10-tooling.md`'s RQ-T-2 belongs to `colbymchenry/codegraph` specifically, measured across seven repositories (VS Code, Excalidraw, Django, Tokio, OkHttp, Gin, Alamofire) on Claude Opus 4.8 by the tool's own author, and it does not survive independent replication intact: a third-party test on a repository outside the published suite reproduced the tool-call reduction in the same ballpark (55% versus the published figure) but found the published cost saving reversed into a 6.8% cost increase. `colbymchenry/codegraph` is the stronger candidate on maintenance signal (964 commits, MIT, incremental file-watcher-driven re-sync, 42 contributors, third-party-filed issues and pull requests) and on the record's own selection in `docs/prd/inputs.md` (row 3, decided by the user); `codegraph-ai/CodeGraph` is Apache-2.0, broader in raw language count (38, versus an unstated exact count for the other) and MCP tool surface (42 tools in its free tier), but weaker on external-use signal (75 stars, 14 forks, "maintained by a solo developer" in the project's own words) and its exact last-commit date could not be pinned from the fetched page.

**Patterns found.**
- `colbymchenry/codegraph`: MIT licence; 964 commits on `main`; latest release carries SLSA v1.0 Build Level 2 attestations dated July 2026 or later. Java is explicitly listed as fully supported via the `.java` extension. Index is stored in a SQLite database (`.codegraph/codegraph.db`) with FTS5 full-text search and WAL for concurrent access. Updates incrementally via native file watchers (FSEvents, inotify, ReadDirectoryChangesW) with debounced auto-sync; a full re-index is available but not required after the initial build. Ships as a self-contained CLI with a bundled Node runtime and an MCP server reachable via `codegraph serve --mcp`; one primary MCP tool (`codegraph_explore`) is listed by default, with six further tools (`node`, `search`, `callers`, `callees`, `impact`, `files`) plus `status` available but unlisted. — GitHub, `colbymchenry/codegraph`, `https://github.com/colbymchenry/codegraph`, official repository, fetched directly.
- Evidence of use beyond the author: 42 contributors per GitHub's contributor graph; 4,195 forks; third-party-filed issues, including a documentation-improvement issue (#305, "add Contributing section to README") and a feedback-request issue (#1021) that are not the author's own commits. Star count (roughly 66.7k-69.4k across two fetches taken days apart) is noted per the packet's own rule that stars are not evidence and is reported here only for completeness. — GitHub contributor graph and issue tracker, `https://github.com/colbymchenry/codegraph/graphs/contributors`, `https://github.com/colbymchenry/codegraph/issues/1021`, `https://github.com/colbymchenry/codegraph/issues/305`; star counts from `https://www.star-history.com/colbymchenry/codegraph/` and a direct repository fetch — official repository and a secondary stats aggregator, both search-derived, not independently cross-checked against each other's exact figures within budget.
- The benchmark: "88% fewer tool calls, 53% faster, 62% fewer tokens, 44% cheaper, file reads cut to zero," measured on seven open-source repositories spanning seven languages, at the median of four runs per arm, on Claude Opus 4.8, re-measured 2026-08-05, with a harness that blocks the `codegraph` CLI in both the with- and without-CodeGraph arms. — search-derived summary of the project's own published benchmark page, author-reported, not independently re-fetched from the primary benchmark page within this pass's budget.
- Independent replication: on Hono (~280 TypeScript files, outside the published seven-repo suite), tool calls fell 55% (14.0 to 6.3 average) against a published 71% claim — "same ballpark" per the tester — but cost rose 6.8% against a published 35% saving, and latency fell 20% against a published 46% claim. The tester, Harrison Guo, states explicit non-affiliation with the project and frames the test as a check on "designer bias," calling it "the #1 risk" of self-reported benchmarks. — HarrisonSec, "I Tested CodeGraph on Hono. The Tool-Call Savings Reproduce — the Cost Savings Don't," `https://harrisonsec.com/blog/i-tested-codegraph-on-hono-benchmark/`, independent practitioner report, fetched directly.
- `codegraph-ai/CodeGraph`: Apache-2.0 licence; 148 commits on `main`; extension version 0.20.1 referenced, no specific release date surfaced. 38 languages including Java, explicitly grouped under "JVM" alongside Kotlin, Scala, Groovy, and Clojure; some languages (COBOL, Fortran, Perl, Dart, Zig, R) require a separate build flag and are not in the default binary. Index persists to `~/.codegraph/graph.db` via RocksDB, with vectors stored alongside the graph; incremental re-indexing on file changes uses FNV-1a content hashing, giving instant startup on restart without re-parsing or re-embedding. Exposes 42 MCP tools in the free tier, plus 27 more (17 of them security analyzers) in a paid "Pro" tier, for 69 tools total if both are attached. 75 stars, 14 forks, 2 open pull requests from other contributors; the project's own README states it is "maintained by a solo developer." — GitHub, `codegraph-ai/CodeGraph`, `https://github.com/codegraph-ai/CodeGraph`, official repository, fetched directly.
- Other projects surfacing under a "codegraph" or "code graph" search are differently named or unverified within this pass's budget and were not fetched: `nahisaho/CodeGraphMCPServer` (GraphRAG-style, no external database, not checked for Java or maintenance signal), `CartographAI/mcp-server-codegraph` (Python/JavaScript/Rust only, no Java mentioned in the search snippet), `entrepeneur4lyf/code-graph-mcp` (hyphenated name, 25+ languages including Java per the snippet, not independently fetched), `websines/codegraph-mcp` and `CodeGraphContext/CodeGraphContext` (not fetched). None of these was verified against the packet's licence/last-release/Java-explicit/MCP-tool-count bar within this pass's search-and-fetch budget. — search snippets only, not fetched.

**Evidence quality.** Primary for licence, language coverage, index storage, update mechanism, and MCP tool count on both `colbymchenry/codegraph` and `codegraph-ai/CodeGraph` (both repositories fetched directly). Primary and independent (not the author, explicitly disclaiming affiliation) for the partial-replication finding on the token-reduction benchmark, which is the strongest evidence-of-use-beyond-the-author found for either project on the specific benefit claim; the underlying seven-repo benchmark itself remains author-reported and was not re-fetched from its own primary page in this pass. Contributor and issue-tracker evidence for `colbymchenry/codegraph` is primary (GitHub's own graphs) but star-count figures came from two different fetches days apart with materially different numbers (66.7k versus 69.4k), which the packet's own rule already discounts as non-evidence, and the discrepancy itself was not investigated further. The four further "codegraph"-adjacent projects listed above rest on search snippets only and were not verified against the packet's bar.

**Fit to the inputs row.** Row 3 needs "a code graph or symbol index, so agents navigate by structure instead of grep," citing FM-14, FM-03, FM-02, C1, with the MVP wording "LSP-based symbol tools through an MCP server" and the user's decision in section 6 to select "codegraph (colbymchenry)" over Serena, with an open question on attachment path (CLI from a script versus the MCP server by exception) under the no-third-party-MCP rule, and a requirement that the `.codegraph/` index "must be refreshed on merge" (FM-17). This packet's findings sharpen three things the row's note gets wrong or leaves open: first, `colbymchenry/codegraph` is not LSP-backed the way the row's MVP wording and the R10-tooling.md RQ-T-2 comparison against Serena implies — it is a tree-sitter-plus-SQLite/FTS5 knowledge graph with file-watcher-driven incremental sync, closer to the row's "Later: a persistent graph" category than to the MVP's "LSP-based symbol tools," which means the freshness story is a file-watcher's own liveness, not a language server's, and the row's FM-17 refresh-on-merge concern is real and unaddressed by any documented "invalidate on merge" hook — auto-sync watches local file changes, not merge events, so a merge that lands from outside the watched working tree (a separate clone, a CI checkout) would leave the index stale until a full re-index is triggered by hand or by a script the factory would have to write. Second, on C1's schema-cost point, `colbymchenry/codegraph` documents one MCP tool by default (`codegraph_explore`) with six more available but unlisted, which is a smaller default schema footprint than Serena's un-trimmed 29 tools noted in `R10-tooling.md`, but the alternative candidate `codegraph-ai/CodeGraph` exposes 42 tools by default, which would cost far more schema context if it were substituted — the row's attachment-path note should specify which tool subset is actually attached, not assume the whole server. Third, the benefit claim the row's note calls "self-reported": this packet found one independent, non-author replication (HarrisonSec) that partially confirms the direction of the tool-call and latency claims but explicitly contradicts the cost claim on a repository outside the vendor's own test suite — this is the first non-vendor data point either research packet has found for this specific tool, and it argues for treating the cost-reduction figure as unconfirmed even though the tool-call-reduction figure has weak independent support, a distinction the row's flat "self-reported" note does not currently draw.

**Gaps.** No published "invalidate the `.codegraph/` index on merge" mechanism was found for `colbymchenry/codegraph`; auto-sync is described only in terms of local file-watcher events, and what happens when a merge lands via CI or a second clone (rather than a file change the watcher observes) was not documented on the fetched page and was not found via search within budget. `codegraph-ai/CodeGraph`'s exact last-commit or last-release date could not be pinned from the fetched page (only a commit count and an extension version number were surfaced), so its status under the packet's twelve-month unmaintained rule is unresolved. The seven-repo benchmark's own primary page was not independently fetched in this pass; the benchmark figures rest on a search-derived summary of the author's own page, corroborated only indirectly by the Hono replication's own quoted figures. Four further "codegraph"/"code-graph"-named MCP projects surfaced in search were not fetched or checked against the licence/Java/maintenance bar (`nahisaho/CodeGraphMCPServer`, `CartographAI/mcp-server-codegraph`, `entrepeneur4lyf/code-graph-mcp`, `websines/codegraph-mcp`, `CodeGraphContext/CodeGraphContext`) and should be treated as unverified rather than ruled out.
