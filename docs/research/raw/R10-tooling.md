### RQ-T-1. Which OpenTelemetry GenAI semantic conventions are stable enough to borrow as the ledger schema, and which of Claude Code (CLI and Agent SDK), Cursor CLI, and Cursor SDK expose per-invocation tool-call, token, and cost data locally without an exporter?

**Answer.** No part of the OpenTelemetry GenAI semantic-convention family is Stable as of mid-2026; every span, metric, event, and attribute in the dedicated `gen_ai.*` repository carries the "Development" stability badge, and the family was split out of the core semantic-conventions repository into its own faster-moving release track in v1.42.0 (June 2026) without being graduated. The conventions are shaped well enough to borrow as a naming scheme (operation name, request/response model, token usage) but nothing in them should be cited as a stable contract, and they define no `cost` attribute at all. Of the four runtimes named, only Claude Code (CLI and Agent SDK) documents concrete per-invocation token and cost fields, now confirmed by direct fetch of both the hooks reference and the Agent SDK cost-tracking guide; Cursor CLI's own output-format page, fetched directly, documents no tokens, cost, or per-tool-call duration in either output mode; and Cursor's own documentation index, fetched directly, contains no page describing a distinct SDK, so "Cursor SDK" is confirmed undocumented rather than merely unverified.

### RQ-T-2. Which open-source code graph or symbol index tools are maintained, expose an MCP server, cover the mainstream service languages, and can be rebuilt or invalidated on merge?

**Answer.** Serena is the clearest maintained, MCP-native, LSP-backed candidate, covering upwards of 40 languages through per-language language servers, MIT-licensed, and under active development; it does not persist a graph, so "rebuild on merge" does not apply to it in the way it does to a SCIP-based index — its index is the live LSP session, which is stale only to the extent the underlying language server's own workspace view is stale. SCIP indexers (`scip-python`, `scip-typescript`, `scip-java`, `scip-go`) are Sourcegraph-maintained, Apache-licensed, and cover the language matrix, but they produce a static index file that must be explicitly regenerated on every merge and none of them ships its own MCP server — an MCP layer would have to be built or borrowed. A direct fetch this pass found `scip-python` has no tagged GitHub releases at all ("There aren't any releases here"), which weakens its maintenance signal under the packet's own twelve-month rule even though the repository shows thousands of commits; `scip-typescript`'s latest tagged release is v0.4.0, dated October 2, with the year not stated on the fetched page, so its currency could not be fully pinned down either. Aider's repo-map is a tree-sitter-plus-PageRank summary, not an MCP server or a persistent graph, and is the clearest example of the third category the row names ("a repo-map summary"). No independently measured, denominated comparison of structural navigation against grep was found for any of these tools; every reduction figure encountered was an unverified third-party or vendor-style claim.

**Patterns found.**
- Serena: MIT licence, "actively maintained," MCP server built in, 30+ (per one source) to 40+ (per the repository's own language list) languages via Language Server Protocol, with a JetBrains-plugin backend as a paid alternative to the open LSP backend. Tools include `find_symbol`, `find_referencing_symbols`, `rename_symbol`, `replace_symbol_body`, `insert_before_symbol`/`insert_after_symbol`. — GitHub, `oraios/serena`, `https://github.com/oraios/serena`, official repository, fetched directly.

### RQ-T-3. What does a minimal durable workflow engine cost to run on one machine, and at what concurrency is a SQLite state table known to fail as a job queue?

**Answer.** Temporal's dev server is a single zero-dependency binary that persists to SQLite by default, but Temporal's own documentation limits SQLite to testing and development and requires Postgres, MySQL, or Cassandra (plus Elasticsearch for advanced visibility) for production; retries and timeouts are expressed as `RetryPolicy` and `StartToCloseTimeout`-style workflow/activity options, which map cleanly onto D14's per-tier token-and-wall-clock bounds as configuration rather than code. Prefect and Dagster both default their local/dev servers to SQLite and describe it as adequate for single-user or local development, with both vendors' own guidance naming locking and lack of connection pooling as the reason to move to Postgres once load grows, though neither publishes a concurrency number at which SQLite is known to fail. The general SQLite literature converges on one writer at a time under WAL, with "lock errors negligible" reported below roughly 20 concurrent writers and p99 latency degrading above that threshold; no source in this pass reports a concrete failure at anywhere near the PRD's one-to-three-ticket concurrency, so the parallel-ticket limit in section 8 is well inside every documented safe zone, not near a known failure point. This question was not in the coordinator's verification-pass priority list and no new fetches were made against it in this pass; its sourcing is unchanged from the first draft and remains search-snippet-derived throughout.

**Patterns found.**
- "The local development Temporal Service runs as a single process with zero runtime dependencies and it supports persistence to disk and in-memory mode through SQLite." — Temporal Documentation, "Run a development server," `https://docs.temporal.io/develop/run-a-development-server`, official tool documentation, search snippet only.
- "Embedded deployments with SQLite are suitable for testing and development only. For production workloads, deploy Temporal as a service using MySQL, PostgreSQL, or Cassandra as the persistence layer." Advanced Visibility (search/filter over workflows) additionally needs Elasticsearch or a SQL database from version 1.20 onward. — Temporal Documentation, "Persistence," `https://docs.temporal.io/temporal-service/persistence`, official tool documentation, search snippet only.
- "SQLite is recommended for lightweight, single-server deployments... A local SQLite database is the default database... located at `~/.prefect/prefect.db` by default," but "SQLite is fine for local/dev but struggles under load (locking, big queries, no pooling)... the single biggest improvement is switching to Postgres" once databases reach multi-gigabyte size with spikes. — Prefect Documentation, "Prefect server," `https://docs.prefect.io/v3/concepts/server`, official tool documentation, search snippet only, no specific concurrency figure given.
- "The most simple setup with `dagster dev` uses a SQLite database, which has been found to be perfectly sufficient for local development," swappable for `PostgresRunStorage`. — Dagster Documentation / community discussion, `https://docs.dagster.io/deployment/oss/oss-deployment-architecture`, official tool documentation, search snippet only, no concurrency figure given.
- "WAL mode is the modern default for any SQLite database with concurrent access, because it lets readers and writers proceed in parallel," but "concurrency for writes is exactly one, meaning SQLite can only handle a single writer at a time," and one practitioner benchmark reports "lock errors become negligible for workloads under 20 concurrent writers, but p99 latency degrades... beyond that threshold," with WAL cutting p99 latency 30-60% versus rollback-journal mode above two concurrent writers. — practitioner blog, grade C, single-author benchmark with no disclosed methodology or hardware spec beyond the post itself: "Where SQLite Gives Up," `https://gauravsarma1992.medium.com/where-sqlite-gives-up-locks-writers-and-the-single-file-problem-69ea745d0c3b`, search snippet only; a second similarly-styled post repeats comparable figures without an independent dataset, `https://shivekkhurana.com/blog/sqlite-in-production/`, search snippet only.
- `litequeue`, a small SQLite-backed job queue, uses "a reentrant write lock" to prevent concurrent consumers claiming the same message and an explicit `queue.transaction()` to exclude other writers; its own repository ships a benchmark script comparing it to Python's in-memory `queue.Queue`, but no published number for a specific concurrent-worker count at which it breaks was found. — GitHub, `litements/litequeue`, `https://github.com/litements/litequeue`, official repository, search snippet only.

**Evidence quality.** Unchanged from the first draft. Primary for what each orchestrator documents about its own default persistence and its own recommendation to move off SQLite, though this is search-snippet-derived rather than independently fetched in either pass. The write-concurrency figures come from two single-author practitioner blog posts with no disclosed benchmark methodology, hardware, or SQLite version — grade C. No source in this pass reports running an agent pipeline's own state on SQLite at one to ten concurrent units of work.

**Fit to the inputs row.** Unchanged. Rows 5 and 6 need "a SQLite state table" (MVP) and "durable workflow or DAG orchestration" (Later, "adopted when the state table demonstrably fails," D24, D27). Nothing found in this pass suggests the state table fails anywhere near the PRD's parallel-ticket ceiling of one, then two, then three (section 8): every concurrency figure located, however weakly sourced, puts SQLite's rough safety margin under WAL at an order of magnitude above three concurrent writers, supporting D24's threshold as currently conservative rather than premature.

**Gaps.** Unchanged: no published concurrency-failure number specific to a durable-workflow-engine SQLite backend, and no published account of an LLM-agent pipeline's own orchestration state on SQLite at any specific concurrency. ### RQ-T-4. Which git-backed or local issue trackers built for agents exist, and does any have evidence of use beyond its author?

**Answer.** Three maintained candidates were found: Beads (Steve Yegge), git-bug, and Backlog.md. Beads is MIT-licensed, stores state locally (SQLite with JSONL export for git-based sharing), ships a CLI and a Python MCP integration, and has moved past single-author use with 29 external contributors and community forks (a Rust port, a separate web viewer); its "tens of thousands of users" figure, however, is the author's own unaudited claim. git-bug is GPLv3, stores issues as native git objects (no extra files in the repository), and has the strongest external-use signal of the three by conventional open-source measures (124 contributors, an Open Collective funding page, 9.4k stars), but it is a general distributed bug tracker, not agent-specific, and carries no built-in question/answer/assumption schema. Backlog.md stores tasks as per-task markdown files under `backlog/tasks/` in the repository, ships an MCP server, and documents support across several agent runtimes (Claude Code, Codex, Gemini CLI, Kiro, Cursor), but its adoption evidence beyond the author is thin and largely self-reported ("dogfooded," per its own README). None of the three publishes a schema matching the PRD's `ticket`/`question`/`answer`/`assumption` tables field for field; all lose the PRD's ranking, consequentiality, and blocking-state fields. This question was not in the coordinator's verification-pass priority list and no new fetches were made against it in this pass.

**Patterns found.**

### RQ-T-5. How do existing factories record agent cost per unit of work, and does any publish its schema?

### RQ-T-7. What does the GitHub MCP server expose for workflow runs, check runs, and job logs, and what does it not?

**Answer.** The official `github/github-mcp-server` (MIT licence, confirmed by direct fetch) exposes an `actions` toolset with three read-only tools — `actions_list`, `actions_get`, and `get_job_logs` — and one write tool, `actions_run_trigger`, which a read-only factory must never attach. A direct fetch this pass corrects the first draft's stated gap: check runs and check suites are covered, but not inside the `actions` toolset — they are exposed through a `get_check_runs` method on the `pull_request_read` tool, described in the server's own documentation as "check runs for the head commit of a pull request... the individual CI/CD jobs and checks that run on the PR," which is part of the `pull_requests` toolset (one of the five toolsets enabled by default), not the `actions` toolset. This means a factory that enables only the `actions` toolset would miss check-run data entirely and must also enable `pull_requests` (or call `get_check_runs` specifically) to get it — a more precise finding than the original draft's blanket "no Checks-API tool found." `get_job_logs` takes `owner`, `repo`, `job_id`, `run_id`, `failed_only`, `return_content`, and `tail_lines` as parameters; no documented byte-size or line-count limit beyond the optional `tail_lines` truncation was found in either fetch. The `--read-only` flag (or `GITHUB_TOOLSETS`/`--toolsets` configuration) is confirmed as "a strict security filter that takes precedence over any other configuration, by disabling write tools even when explicitly requested," which is the mechanism a factory would use to keep `actions_run_trigger` off the allowlist. On credentials, a direct fetch of GitHub's own remote-server setup documentation states the remote server accepts OAuth ("one-click... by default... you do not need to create a PAT") or a manually-configured personal access token; GitHub's own page makes no mention of GitHub App installation tokens as a supported credential for the MCP server, so the first draft's claim (previously resting only on a third-party blog) is now confirmed from GitHub's own silence on the matter, not from Scalekit's analysis — this is a meaningfully different evidentiary basis even though the practical conclusion is unchanged.
