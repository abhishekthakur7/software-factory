# 2.3 Ticket states

Part of the [Software Factory PRD](prd.md). The index holds the version, the reading rules, and the map from section numbers to files.

States are the only orchestration the initial version has (D24, D27). A stage may run only from the state that precedes it, and a stage's outcome moves the ticket to exactly one next state. Every wait on a human is a `queue_item`; `blocked_on` names it. A human pause holds the current state rather than inventing a parallel stage state, and the runner checks the pause flag between every recorded boundary (R-H-13).

| State | Entered from | Leaves when |
|---|---|---|
| `intake` | Ticket picked up; also where a ticket beyond the parallel limit waits (R-I-10) | S0 scripts pass and the human decides eligibility (`eligibility` item); a mechanical failure or a decline goes to `rejected` |
| `rejected` | S0 fails the mechanical gate, the ticket is outside pilot scope, the human declines, or S1/S3/S5 discovers an Initial exclusion | Terminal; `close_reason = rejected_at_s0` or `pilot_excluded`, with the discovered reason and evidence |
| `context` | Eligibility granted; a send-back or base refresh from any later state | S1 passes; an S1 blocker is a blocking question and the run ends `blocked`; an Initial exclusion goes to `rejected` |
| `clarifying` | S1 pass; a send-back from any later state | S2 exit (R-S2-12) with no open blocking question; an S2 run that raises a blocking question ends `blocked` and reruns from the record when it is answered |
| `planning` | S2 exit; a send-back from `plan_review`, `checks`, `review`, or `escalated` | S3 produces the criteria-and-plan approval bundle; an Initial exclusion goes to `rejected` |
| `plan_review` | Plan produced (`plan_approval` item) | Every required role must approve the same plan subject. Before the action commits, a trusted guard fetches the target branch and requires its head to equal the plan tuple's `base_sha` and recorded target-base SHA. Full quorum plus equality moves to `implementing`; a mismatch starts no S4 work and permits only recorded `refresh_base` to `context`, send-back, or abandon. Redirect returns to `planning`, `clarifying`, or `context` with a `send_back` tag and note |
| `implementing` | Current plan subject approved; request changes from `review`; send-back from `checks`; a trusted `sync_pr_head`; an eligible resolved escalation | S4 records a successful hand-back with branch, head SHA, and explicit deviation list and enters `checks`. A stale-binding preflight starts no agent, queues one `red_check`, and remains blocked in `implementing` until `refresh_base` returns to `context`, send-back, or abandon. The third verification failure, exhausted infrastructure retry, budget abort, sandbox violation, invalid recipe-policy binding, or stop enters `escalated` without changing that run's own outcome |
| `checks` | Successful hand-back recorded | S5 preflight either creates one review tuple or writes one `review_tuple_preflight` failure. A missing/malformed hand-back returns to `implementing`; stale base permits only refresh to `context`, send-back, or abandon; an accidental Initial-sensitive path may return to S4 for removal, while a path required by the plan closes `pilot_excluded`; a new/unresolved non-sensitive reviewer requirement returns to planning or S4 removal; sandbox-integrity failure escalates. Otherwise all blocking results must be `pass` or validly waived `blind_spot`. Then one S6 race-guard and packet/PR-body assembly run executes from `checks`; only its `pass` queues `packet_approval` and enters `review`. A stale binding follows its refresh/send-back route; other S6 failures follow the ordinary stage retry. S5 failures and waivable blind spots queue one `red_check` item for send-back, permitted waiver, or abandon |
| `review` | Passing S6 assembly run (`packet_approval` item) | Every required final-review role must approve the same review subject. Full quorum atomically creates `pr_create` when no PR identity exists or `pr_update` otherwise. A matching reconciled receipt moves to `pr_opened`; an ambiguous effect remains here until reconciled. A pre-dispatch subject, authority, base, head, or destination mismatch supersedes the intent and routes to `checks`, `planning`, or `context` as applicable; a non-retryable permission/control failure escalates; an already closed or merged remote PR routes to outcome capture. Request changes returns to `implementing` with a `revision_after_approval` tag and note, or sends back earlier |
| `pr_opened` | Reconciled `pr_create` or `pr_update` succeeded | First create sets `factory_completed_at`; update increments `external_revision_count`; exactly one current non-blocking `pr_outcome` item remains. Initial: the human records merge, abandonment, or a requested revision; revision invalidates final approval and returns through the selected earlier stage while the remote branch remains unchanged until a new approved `pr_update`. No S7 poll runs. Later: S7 enters `pr_checks` |
| `pr_checks` | `pr_opened` (Later) | Remains while the PR is open. Red, incomplete, cancelled, or skipped required checks leave one immutable `red_check` item whose display is derived from the latest external check rows; the human may wait, send back, or abandon. PR-head movement invalidates final approval and queues human failure-mode classification; `sync_pr_head` fetches the exact remote SHA in a trusted step, preserves conflicting local work, registers the imported revision, and returns through S4 for a fresh deviation list before S5. Target-base movement invalidates the plan binding and permits only refresh, send-back, or abandon. A merge-group SHA is recorded separately; only movement of its target-base parent relative to the bound target invalidates the plan. A closed-unmerged observation stops polling and queues outcome classification; an observed merge always enters `merged`, with any stale binding or non-green check recorded as a control defect rather than hidden |
| `merged` | Initial: human records the observed merge, actual head/base/body, merge SHA, checks and approval disposition. Later: S7 detects it. Either path records reality even when it exposes a stale-approval control defect | Terminal; `closed_at`, `close_reason = merged`, and a current production-coverage record are required. `unknown` is allowed at close but cannot satisfy graduation; `none_observed` requires recorded exposure |
| `abandoned` | Human classifies a close without merge from any state, including Initial `pr_outcome` or Later closed-PR observation | Terminal; requires an `abandoned` tag, `not_deployed` production-coverage record, and `closed_at` |
| `escalated` | A stage exhausts its retry/budget/verification bound, hits a non-retryable permission/control failure, violates sandbox integrity, or is stopped; an `escalation` item records the cause and failed run or external-write intent | Verification exhaustion may only move to `planning` or earlier for a superseding plan-item version and new approval, or abandon. Budget change follows manifest migration and reapproval. An execution-boundary, recipe-policy, permission, or other control defect resumes only after a factory fix passes R-F-14, its disposition is remediated, and the ticket migrates where applicable. Infrastructure exhaustion or human stop may resume the same stage with verification count preserved. Every path carries the resolution note; any path may abandon |

**Send-back.** From any open queue item (plan approval, red check, packet approval, escalation, or manual pause) the human may send the ticket back to `context`, `clarifying`, or `planning` with a `send_back` tag and a note. The target stage reruns with `attempt + 1` and receives the note; artefacts produced after it are superseded and their evidence tuples invalidated. This is the stable-boundary intervention P11 asks for; it is not steering inside an invocation.

**Failed and blocked runs.** Outside S4, a run ending `fail` or `infrastructure_failure`, including an R-I-12 structural failure or expired lease, leaves the ticket in its current state; `advance` starts the single configured fresh rerun with `attempt + 1`, then moves to `escalated` if it also fails. S4 uses R-S4-5's separate three-verification bound: infrastructure runs do not consume it, and a superseding plan-item version plus new approval begins a new bound. S4 stale-binding and control-defect outcomes follow their explicit human/fix routes and are never automatically retried. On restart, the runner expires only a run whose lease and process identity are both dead, records `infrastructure_failure` with `failure_kind = expired_lease`, preserves registered outputs and the worktree, and reconciles pending external writes before any state advance. A run ending `blocked` writes its artefact with answer-dependent sections marked `pending answer`, exempt from R-I-12 until the fresh rerun, which receives the prior artefact but no hidden transcript.
