# S4 Implementation

Section 4 of the [Software Factory PRD](prd.md), one file per stage. The index holds the version, the reading rules, the rubric-line conventions, and the map from section numbers to files.

S4 is automated from the initial version (D20): the factory runs the implementation through the primary runtime, one fresh invocation per plan-task attempt, under the D14 bounds, in a sandboxed isolated worktree on a ticket branch. Nothing is pushed until the engineer approves the packet at S6. The hand-off and hand-back fix what S5 and S6 need whoever produced the change, so an external implementer stays possible.

| R-S4-5 | Automated S4 uses one fresh `stage_run` per plan-task execution, in dependency order, in the sandboxed ticket worktree. Immediately before each invocation, the trusted runner revalidates the exact plan subject, approval quorum/authority, trust approvals and expiry, fetches the target, and requires its head to equal the plan tuple's base and recorded target head; mismatch starts no agent, records `fail/stale_binding` with null `verification_attempt`, queues one `red_check`, and remains blocked in `implementing` until the applicable governance repair, refresh, send-back, or abandon. After a successful invocation reaches validation, the runner assigns the next `verification_attempt` and executes each approved typed recipe exactly once. Green recipes produce `pass`; implementation or validation failure produces `fail` and consumes one of three verification attempts per approved plan-item version. Unavailable approved runtime infrastructure is `infrastructure_failure` and receives the ordinary single retry without consuming that quota. An unapproved recipe or invalid approved-recipe binding is a control defect and escalates immediately without consuming verification quota. Each retry is a fresh invocation receiving registered evidence, never a continuation. Only named tasks rerun after feedback, and retained task results remain valid only while plan-bound inputs are unchanged. | D14, D28, P6, P10, FM-19, FM-21, FM-25 | Initial | Pre-task subject/base/authority race, three-verification, infrastructure retry, control-defect, fresh-context, recipe, plan-version, and selective-rerun tests |
| R-S4-6 | The third verification failure remains outcome `fail` and atomically moves the ticket to `escalated` with complete per-attempt failure history and an FM-19 escalation tag. A repeat infrastructure failure escalates as `infrastructure_failure` without consuming verification quota; budget and human stops retain `aborted_budget` and `aborted_human`. A sandbox-integrity, undeclared-capability, or invalid recipe-policy binding records the applicable failure outcome, writes a matching `control_defect` tag (FM-23 when the execution boundary is implicated), opens an execution-boundary control-defect event, and escalates immediately. Resuming after verification exhaustion requires a superseding plan-item version and new S3 approval; infrastructure or human-stop resolution may resume the same item with quota preserved, while control-defect resolution requires a factory fix, remediated disposition, and R-F-14 pass. | P1, P7, P10, FM-19, FM-23, FM-09 | Initial | Atomic outcome/state, quota, cause-tag/event, resume-policy, and failure-history tests |
| R-S4-7 | The advisory tier (R-S5-8) enforces the two checklists the handoff carries. Comment rules: a comment fails if it can be regenerated by paraphrasing the adjacent code; a comment is required where the plan marked a decision non-obvious or where behaviour deviates from what the name or signature implies; TODO comments carry an owner. Test filter: a generated test is kept only if it builds, passes N reruns without flake, raises coverage or kills a mutant the existing suite missed, and states what it proves. | P6, FM-11, FM-12, FM-13 | Later | Grader on recorded fixtures |

**Rubric, S4.** R-S4-2: deterministic, deviation list present and well-formed; synthesis S4, original schema. R-S4-5: deterministic, typed task-validation recipes run by the runner; original, from the v0.5 review.

**Human touchpoint.** None during normal implementation. A stale-binding `red_check` requires refresh, send-back, or abandon; an escalation requires the cause-specific action in R-S4-6.
