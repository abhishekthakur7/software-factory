# 11. Decisions this document makes beyond the charter

Part of the [Software Factory PRD](prd.md). The index holds the version, the reading rules, and the map from section numbers to files.

Each is a judgment call the charter does not settle. Veto here, not in the requirements. Calls 1 to 19 were accepted by the owner on 2026-09-04; 9, 10, 12, 13, 15, 17, and 18 were later tightened and stood. Calls 20 to 28 were accepted after the v0.5 review and revised where v0.8 changed the pilot boundary. Calls 29 to 39 record the owner's answers to later review rounds. Calls 40 to 47 adopt the requirements-boundary recommendations in v0.8.

1. **Artefacts are files with database pointers**, not blobs in SQLite, so humans and agents read the same thing and versions diff.
2. **S0 is scripts, the scrutiny paragraph included**: a template keyed on type, title, tier and sensitive paths fills it and the human edits it at eligibility; ticket type comes from the Jira issue-type mapping with human confirmation, so no agent judgment is spent before eligibility. The agent draft of earlier versions was withdrawn on 2026-09-07: it paid for a sandbox, model checks and cost settlement to draft one paragraph from two fields.
3. **The tier matrix and the final-tier rule** are the values in section 8. They are guesses until pilot data replaces them.
4. **The Heavy size gate is tighter than Standard**, 200 against 300, because reviewer attention per line matters more on Heavy tickets.
5. **The initial formalisation check is an agreement heuristic** over N independent restatements, not a solver or completeness proof. Disagreement exposes ambiguity; the S3 reviewer supplies the uncalibrated semantic verdicts.
6. **Consequence and reversibility are separate.** `consequential` means touching a contract, migration, permission boundary, public interface, rollout strategy, or sensitive path. `hard_to_reverse` means rollback cannot cheaply restore prior data, interface, authorization, or customer-visible state. A default is withheld only when both are true, except mandatory-human security/data decisions.
7. **The S2 split threshold is 60 percent of the size gate**, so a split is proposed before the plan is written rather than after the diff exists.
8. **Contract evidence is split by claim.** Language tooling checks public/protected source-declaration shape where a grammar exists. Tests, characterization evidence, and recorded human judgment cover behavioural contracts. Missing coverage is a named blind spot, never implied verification.
9. **S4 is automated from the first version** through the primary runtime under the D14 bounds and R-I-14 sandbox. The human still gates at plan approval and final review. The hand-off and hand-back remain a protocol so an external implementer stays possible; a missing deviation set is a non-waivable structural hand-back failure, while no deviations are represented by a canonical empty deviation set.
10. **The review comes before the draft pull request.** The engineer reviews the local packet with its diff; only on approval does a trusted outbox worker push the branch and open or update one draft PR using the separate narrative body. Draft-PR creation completes the factory phase, not the ticket outcome.
11. **Tags classify evidence at its source.** Human judgments remain human-written. The factory writes only `stale_index`, cause-specific `escalation`, and mechanically detected `control_defect`; checks otherwise name a likely catalogue id for the human to confirm.
12. **Approval validity follows C11's two bindings.** Expected S4 commits create the review binding without invalidating plan approval. Any post-review commit, changed check evidence, changed packet or PR body, or changed required-reviewer set invalidates S6; a changed plan-bound input invalidates S3. Initial records revision cycles manually and S7 later detects them.
13. **A frozen baseline of 10 comparable tickets** is completed before Milestone B under R-O-6. Every requested value has provenance and a status; approximate and unavailable evidence stays visible but cannot satisfy a graduation comparison. If retrospective evidence is insufficient, a separately delimited prospective non-factory cohort completes the revision baseline before the first real factory ticket.
14. **The reporting-rule requirement cites the measures it protects** rather than a failure mode of its own. Gaming of measures is not a catalogue entry, and this document proposes none.
15. **S7 is Later.** In the initial version no agent runs on a ticket after S4; the observer pass, when it arrives, runs over the record, not on the ticket. S7 failure summaries use an agent at Light budget, read-only.
16. **Every run is scored at pilot scale**, once the observer pass runs. Sampling is for fleets. At one to three tickets in parallel the cost is small and every score is calibration data.
17. **Stop is the only mid-invocation intervention.** A durable pause may take effect at the next stable boundary; send-back and inspection happen only at boundaries. Live steering is excluded because it breaks reconstruction and requires a watching human.
18. **`factory/` lives in this repository, the factory repository,** alongside `docs/`. After the scaffold commit, changes are reviewed pull requests gated by R-F-14 even before Later branch protection and calibrated quality evals exist; direct unreviewed default-branch edits are not adoption.
19. **The first benchmark per stage is how the runtime per stage is revisited**, after that stage's graders are calibrated. Until then the manifest carries the Cursor SDK local runtime (call 48), recorded on every run.
20. **Draft-PR creation and ticket close are distinct.** Entering `pr_opened` sets `factory_completed_at`; `closed_at` is set only when the human records `merged` or `abandoned`. Initial uses the manual R-H-11 loop and automated S7 later replaces it.
21. **The self-improvement scaffold has an Initial mechanical gate.** Synthetic, redacted smoke/conformance fixtures and R-F-14 exist before Milestone B and gate every reviewed factory change after the scaffold commit. Observer scoring, calibration, holdout quality evals, benchmarks, and the improvement agent are Later. Until calibrated, semantic authority remains with the recorded human verdicts.
22. **Sensitive work is excluded from Initial.** Candidate and actual sensitive paths still resolve their owner so the exclusion is testable. After a reviewed graduation decision admits such work, the factory requires a distinct owner at S3 and S6; GitHub required-reviewer enforcement remains Later.
23. **Mechanical pilot exclusion carries no human failure tag**, whether detected at S0, S1, S3, or S5. Its rule and evidence are recorded. Human decisions against factory output carry their own tags; the factory writes only the three mechanical classes named in call 11.
24. **Escalations are their own queue-item kind**, not questions, because they carry a failure history rather than options and a default.
25. **Rubric lines are requirement rows.** Rubric files are generated from the rows named in each stage's rubric list, and `score.dimension` is a requirement id. When the file and the row diverge, the file is regenerated.
26. **Retired ids are never reused** (section 13). References in research packets and earlier revisions keep resolving.
27. **The reliability unit at S4 is the plan-task execution.** Every start is its own `stage_run`; `attempt` increments per (`stage`, `plan_item`), while `verification_attempt` carries D14's quota. Pass is determined only by approved recipes. Refused, blocked, human-cancelled, child, and utility runs are excluded and reported separately; infrastructure, sandbox, budget, and ordinary failures remain reliability failures.
28. **The engineer sends back; the engineer does not patch.** A red check or request for changes follows its governed target: S4 for implementation repair, an earlier stage when its evidence is wrong, refresh for stale base, or abandon. No change to the branch happens outside a stage run or the trusted Later `sync_pr_head` import, so the record stays complete (C5).
29. **The plan carries fixed tables.** Scope, dependencies, contracts, tasks, test strategy, and size are tables with named columns (R-S3-18, section 8), inside the plan file rather than a sidecar, so the human reads one document and the scripts read no prose.
30. **A task passes by approved typed recipes.** Every plan task names recipe ids, typed values, and expected results; the runner validates and executes them once per attempt and sets `pass`. Agent-authored shell and agent opinion set nothing.
31. **The Initial contract check makes only source-shape and evidence-link claims.** Tree-sitter compares all public/protected declarations in touched files plus planned units. A separate script verifies that behavioural contract fields point to tests, characterization evidence, or named blind spots. Compiled Java compatibility is a Later upgrade for broader admitted work.
32. **The human can send a ticket back to any earlier stage** from any open item, with a note the rerun receives (2.3, R-H-4). Stop and abandon are no longer the only between-gate interventions; P11 is met by the send-back, not by steering a running agent.
33. **Callers of the pilot service come from optional hand-written index entries.** Context index entries of kind `caller` supply inbound impact where the engineer has written them; otherwise the brief says "callers unknown" as a blind spot and never implies coverage (R-S1-3).
34. **The factory lives in this repository.** `factory/` and `runs/` are here; the pilot service source is outside it. Each ticket uses an isolated clone and worktree under `runs/`, not a linked worktree sharing the engineer checkout's remote configuration.
35. **Restatements are child runs.** The S2 agreement check's fresh-context invocations are `stage_run` rows with `parent_run_id`, counted in the S2 budget and excluded from the first-attempt measure, so C5 holds and the reliability measure is not distorted (R-S2-3).
36. **Questions are written for a reader who has opened nothing.** No factory-internal identifiers in a question or its options, and every option carries its consequence (R-S2-14). From the v0.6 review round: the one question the owner sent back was well-formed and badly worded.
37. **Plan rows cite criteria.** Tasks and tests carry `AC-n` ids and a script proves every criterion is served by a task and a test (R-S3-19), the way section 9 proves every failure mode is served by a requirement.
38. **The advisory pass stays single until it truncates.** Slicing by concern with script consolidation is R-S5-11, Later.
39. **The factory's own build runs through the process.** Each build ticket gets a hand-written brief and plan tables under `docs/build/`, then enters the synthetic/redacted Milestone A fixture suite. The first pilot ticket is not the first execution of the state machine, sandbox, adapters, checks, or recovery paths. Java-specific checks use seeded fixtures until the pilot service is admitted.
40. **Initial is two acceptance milestones.** Milestone A is a no-production-data walking skeleton with stub writes. Milestone B opens one governed draft PR and records its eventual outcome. Passing either does not widen scope automatically.
41. **Data governance is fail-closed.** The content-addressed trust profile, central guard, and current security plus legal/data-governance approval quorum cover every source-to-destination route and persistence/display boundary; Privacy Mode alone is insufficient.
42. **All agent and repository-controlled execution is OS-isolated.** Tool allowlists supplement rather than replace the sandbox, scoped credentials, controlled mounts, and default-deny egress.
43. **External writes use a transactional outbox.** Jira feedback and Slack digests are idempotent; draft PRs use distinct `pr_create` and compare-and-set `pr_update` operations, with the last quorum-completing approval and immutable destination/payload intent committed together and ambiguous effects reconciled before retry.
44. **Factory and service ownership are explicit roles.** One pilot engineer may hold several ordinary-work roles; sensitive work later requires a distinct owner and enforceable recorded approval.
45. **Queue latency is not human attention.** Initial records a coarse human-entered attention bucket at S3 and S6 and collects no focus, keystroke, or editor surveillance.
46. **Expansion is a reviewed evidence decision.** R-O-13 implements every pilot-graduation condition in Charter section 8. Meeting them makes expansion eligible but never automatic; no context measure or unavailable comparator may substitute for a failed condition.
47. **S7 uses polling, not a webhook.** When S7 is enabled, the runner polls GitHub every five minutes while any ticket is in `pr_checks`. A webhook waits for a governed reachable endpoint and is not an Initial prerequisite.
48. **The Cursor SDK runs in its local runtime on the pilot host; the cloud runtime is not used.** The cloud runtime pushes its own branch with Cursor's GitHub credentials before any human review, has internet egress unless an administrator locks an allowlist, starts from a cached build snapshot, and copies the repository to Cursor's cloud for the run, which contradicts R-I-3, R-I-11, R-I-14, and R-T-9. The local runtime returns the resolved model, request id, tokens, duration, status and per-call records at the invocation boundary, takes inline tool and MCP allowlists and custom typed tools, and runs under the R-I-14 sandbox; cost settles shortly after a run and is reconciled against the Enterprise usage events. Owner decision of 2026-09-04 after the adapter and sandbox spikes.
49. **A disjoint, conflict-free base advance was the runner's decision, withdrawn to Later.** Uber's self-healing CI classifies a red run on a stale base and rebases without a human; for one engineer running the factory locally, a human refresh that restarts at context gathering for an unrelated upstream commit costs attention and buys nothing. R-S5-14 lets the runner advance only when the rebase is clean and every upstream path is outside the plan's scope, the touched areas, the diff, and the sensitive paths, records the evidence, reruns task validation and the checks, and leaves the plan approval standing; charter C11 v0.12 said the same. Every other movement stays the human route of R-S5-12. Withdrawn from Initial on 2026-09-07 after the high-level design (charter D43): with one ticket at a time the human refresh is the only base movement, and R-S5-14 is Later, admitted with parallel tickets.
50. **Machine-verifiable check failures get bounded fix rounds before a human is asked.** Uber's build agent fixes lint and test failures in the inner loop and opens the draft PR with the proof attached; its reviewers had been catching what machines should have caught. R-S4-9 gives the agent at most the configured number of fresh, recorded fix rounds when the only red results are the project's lint, compile/type, or unit-test recipes (extended to integration-test recipes by call 54), inside the per-ticket S4 budget and the plan's scope, then reruns S5 in full. Security, dependency, size, scope, contract, freshness, binding, and sandbox failures never enter a fix round.
51. **Tool results live in files, not in the context window.** Uber's largest fleet-wide token saving came from projecting tools into a CLI whose output goes to disk. R-I-17 writes every result as a governed artefact the agent can read by path and returns only small results inline, with sizes recorded per call; C1's per-stage attachment already keeps schemas small, so no discovery layer or gateway is added for a single-user factory.
52. **The scoped, spend-capped runtime key is the one credential inside an agent sandbox.** The Cursor SDK's local runtime authenticates with an API key held by the process that invokes the model, so a keyless sandbox would need the loopback proxy to inject the key on every call, an unspiked path. The owner chose a key scoped to the approved inference endpoint with a spend cap, supplied by the launcher, reachable only through the loopback proxy, recorded by role name and never by value; every other credential stays outside, and build sandboxes hold none.
53. **Base tests change only through the approved plan, and the gate checks the change mechanically.** Horthy's grading slides show the training setup coding models learn from: the agent's edits to test files are thrown away before the hidden tests run, so a model that may edit tests learns that editing them is the cheapest route to green. The owner asked how a genuine test change is told from a shortcut, and separately asked that the factory stay lax at first, with rules rather than numbers and flags rather than refusals. No model judges intent. The plan's test strategy table lists every existing test the ticket will change or remove with the criterion that makes the old assertion wrong or the behaviour-preserving task it serves, the S3 reviewers approve that list before code exists, and the S5 `base_test_diff` script blocks any other change, removal, rename, or configuration exclusion of a base test, using the engineer-declared test-file globs and the test identities the recipes report. A planned change that passes in both the base and head views is flagged as a `blind_spot` for the reviewer, not refused, and whether a planned change narrows what a test asserted is left to the reviewer, who sees each such change with its diff in the evidence table. A `base_test_diff` failure never enters a fix round. R-S4-10 generalises the fix-round rule of R-S4-9 to every S4 run.
54. **Unit and integration tests are mandatory at S5; end-to-end tests run only where the repository already has them.** Iusztin's observation that the implement-and-check loop fails on missing plumbing before it fails on the agent exposed an ambiguity between the plan's three test sizes and the gate's "unit-test recipes". Owner decision of 2026-09-04: small tests run under the unit-test recipe and medium under the integration-test recipe, both planned wherever a criterion needs them and both blocking; large tests run under an end-to-end recipe that the engineer registers by hand only where the repository already has such a suite, and no ticket creates one. Fix rounds extend to integration tests. An end-to-end red goes to the human as a `red_check` rather than a fix round, because it more often signals the environment than the code. Two consequences of the owner's laxness rule: integration and end-to-end results are regression-only, so a test already red at base stays visible as inherited debt and blocks nothing while a test green at base and red at head blocks; and a test recipe whose declared dependencies the sandbox cannot satisfy records a waivable `blind_spot` naming the dependency instead of running, until the sandbox implementation provides it. Unit tests keep the stricter rule of R-S5-10.
