## 0. How to read this document

A **block** is a contract that later requirements plug into: a data shape or an interface that is used across more than one stage, or is the sole mechanism for a charter principle. The design is extensible because every block exists from the first version; the implementation stays simple because each block starts in its thinnest shape. Section 1 lists the 25 blocks. Each gets a Layer 2 section, `docs/design/L2-<block>.md`, written just before the block is coded and not earlier.

A **milestone** is a set of requirement rows that are satisfied together, with one exit test, and the blocks, in the shapes those rows need, that come alive to satisfy them. The PRD accepts the initial version at Milestone A (walking skeleton on synthetic fixtures) and Milestone B (one real ticket to a draft pull request). Section 3 builds Initial in three steps: A is the PRD's Milestone A and the foundation, where every block comes alive; AB tightens the boundary and makes the real connections; B is the PRD's Milestone B. Later is the PRD's Later, unchanged. The first step is the biggest because it lays the foundation; each later step stands on the one before it and is smaller, and nothing a step's rows need is built after it.

**Where a row sits.** A row sits at the first milestone at which every block it needs, in the shape its requirement text and its verification column require, is alive. The two columns are read together: if a test the verification column names cannot run at a milestone, the row is not satisfied there. Needs are blocks in shapes, not other rows: a row that says "passes R-F-14" needs the fixtures-and-evals block with its gate running, not the completion of row R-F-14. A row is never split across milestones and no milestone claims a part of a row; the mechanics an earlier step builds for a row that completes later are simply the block's shape at the earlier step. Blocks come alive at the first milestone where a row of that milestone needs them, in the thinnest shape that milestone's rows need; a block's shape at a later milestone is stated only where a row of that milestone needs the change. Two anchors outside the block tables fix a row's step: the owner's sequencing decisions (the OS policy, the copy-on-write copies, the loopback proxy and the escape suite between A and B; no real outside read or write and no credential but the scoped runtime key at A), and the PRD's one-page version, which lists the contracts Milestone A proves and names the manual outcome record under Milestone B; the graduation gate reads the outcome, exposure and coverage series that first exist there. A verification test that names a condition is satisfied on a seeded row when the row is a policy over recorded results, such as a waiver refused for a non-waivable condition or an escalation cause mapped to its tag; it must produce the condition through the mechanism whenever the verification column names an escape, a denial or an isolation the sandbox enforces, whichever block owns the row.

Appendix A maps every requirement row of the PRD to one primary block, sometimes a secondary one, and one milestone under that rule. When a row changes, that map says which Layer 2 section changes and when the change is due. Section 4 names the reference design every person-facing surface is built to, and which blocks and milestone each of its screens draws on.

Three rules from the charter and PRD apply everywhere and are not repeated: the person is trusted, the runner process is trusted, and anything inside a sandbox is not. Ticket and repository text is untrusted instruction wherever it crosses; it can never select a tool, recipe, mount, model, endpoint or credential. Every content-bearing crossing passes the guard, and every command and invocation passes the stage interface; nothing else invokes an agent or writes the record.

**Which block owns a row.** A row belongs to the block whose Layer 2 section must change when the row changes: the block that owns the data shape or interface the row constrains. When two would change, in order: what an agent's output must contain is rubric; how a stage runs (attempts, budgets, retries, child runs) is run; a state transition is ticket and its state; what a person is shown or asked is queue item and decision, or the question and assumption log for questions; approvals, waivers and reviewer sets are approval and quorum; a hash of a subject and its freshness is binding; a gate script is check; packet and handoff content is artefact; tool-result capture is invocation and runtime adapter; mounts and egress are sandbox; a command definition is recipe; classification and guard decisions are guard; outside reads and writes are external access; checkouts, SHAs and rebases are git trees; measures, views, export and retention are record; a failure-mode event is tag; an operation of the one API that constrains no other block's data is stage interface. The order lists only the blocks that compete for a row: attachment and wiring are manifest, the tree's layout and change path are factory tree and change control, the factory's own tests are fixtures and evals, and each content block owns the files it names. A clause or test whose subject no step of Initial builds, a proposal path or a path-scoped file, is satisfied by that absence and does not move the row; the note says so. A second block is named only when its section must also change. The improvement loop's Later rows belong to fixtures and evals, so the loop is designed in one place, except the enrolled maintenance source, R-S0-9, which is the skill's; the growth those rows will bring to skill and tag is named in section 1.

**Constraints carried into every layer.** One person, one machine, one ticket at a time; the runner and the record are local, model inference is not. One process per `factory` command and no daemon; the digest is a host scheduler entry that runs one command; outbox reconciliation runs at the start of every state-advancing command. No discovery layer, no registry, no model gateway and no MCP gateway process: the loopback proxy is a fixed stage-scoped allowlist with static routes. MCP servers by the owner's rule only: the Atlassian server (read) to the runner at S0 and the agent at S1, codegraph with its single default tool to the agent at S1, S3 and S4, Slack as the digest command's only tool, the GitHub server Later and read-only. Cursor SDK local runtime only; Claude Code is the second adapter, not a fallback. The simplest design that meets the rows: anything no Initial row needs is a Later part, named but not designed.

## 1. The 25 blocks

The blocks fall into three groups. Content blocks are versioned files in the factory tree, read-only at run time, chosen per stage and tier by the manifest and recorded by hash on every run. Data blocks are rows and files in the one local record, written only by the trusted runner. Mechanism blocks are code on the trusted side; the sandbox is the one with an inside. In each table, the initial shape is the block at Milestone A, and the last column is everything it grows into afterwards: at AB or B, or Later where marked.

## 2. Crossings

A crossing is an edge across which something physically moves: a command, a file, a mount, a network call, a credential. The guard sits on every content-bearing one and leaves one `guard_decision` row per judgement. The full statement of what crosses and what never crosses each edge is in Appendix B, carried from the inventory; this table names the edges and the blocks on each side.

| # | Crossing | From | To | Carried by |
|---|---|---|---|---|
| X1 | The person acts | Person | Trusted runner | Stage interface; queue item and decision |
| X2 | The runner writes and reads its record | Trusted runner | Record; git trees | Record; git trees; every data block |
| X3 | The runner dispatches a run | Trusted runner | Sandbox | Invocation and runtime adapter; recipe |
| X4 | The factory tree is read at run time | Factory tree | Trusted runner | Manifest; every content block |
| X5 | The runner reads from and writes to outside systems | Trusted runner | Jira, Confluence, GitHub, Slack, host credential store | External access; guard |
| X6 | The agent reaches the hosted model and attached servers | Sandbox | Hosted model; Atlassian server; registries | Sandbox (proxy); invocation and runtime adapter |
| X7 | Mounts into a run | Record; git trees | Sandbox | Sandbox; artefact; git trees |
| X8 | The person sees outside systems | GitHub, Slack | Person | External access (nothing flows back on this edge) |
| X9 | The factory changes | Engineer's pull request | Factory tree | Factory tree and change control; fixtures and evals |
| X10 | Run findings return to the tree | Record | Factory tree | Fixtures and evals; tag (one governed export at B, the rest Later) |
| X11 | The sandbox wall | Launcher | Sandbox interior | Sandbox |

The "Carried by" column names the mechanism that moves things across the edge; the rows that define each edge are in Appendix B.

## 3. Milestones

Three steps inside Initial: A, AB and B. A and B are the PRD's two acceptance milestones; AB is a step of this document, and its exit test is not a PRD acceptance gate. Each names its purpose, the blocks that come alive or change shape and the shape the step's rows need, the rows that are satisfied in it, one exit test, and what is deliberately absent. A block that appears at one step keeps its shape until a later step names a change, and is alive at every later step whether or not that step's table lists it. Every block at a step passes the same test: a row of that step needs it, as its primary block, its secondary block, or a need its text or verification column names; the Counts table in Appendix A counts primary blocks only, so a block can be alive at a step where it owns no row. The build order inside a step, and the tickets, are `docs/design/TICKETS.md`, written after this document.

### A, walking skeleton

Purpose: the PRD's Milestone A and the foundation of everything after it. All 25 blocks come alive here, each in the shape A's rows need and no thicker: one record, one state table, one run ledger with leases, registered artefacts, typed recipes, one outbox, one command; every stage running for real on the synthetic fixture repository, the guard on every crossing under a trust profile whose outside routes end at stub deliverers, real reviewer sets, the thin sandbox with the scoped runtime key. Eighty-nine rows sit here, the most of any step, because everything later stands on them.

Build order inside A, fixed by `TICKETS.md`: the ledger-and-control phase first, with every stage a stub, proving the record, the state table, leases, artefacts, recipes, the outbox and the command; then the agent side, stage by stage. In the first phase each stage's manifest entry names its stub files, and each stub file has its eval directory and fixture, so R-F-2 holds from the first commit.
